# Design

## 一、根因：查询通道只在空闲节拍到点时排空

### 事实

- VT 线程的命令循环（`internal.rs` 的 `run_inner`）用
  `command_receiver.recv_timeout(VT_IDLE_TICK_MS)` 等待下一条命令。
- 查询走**另一条**通道（`query_receiver`），只在两处被排空：命令批处理**之后**
  （批尾 `drain_queries`）与**空闲节拍到点**时（超时分支的 `drain_queries`）。
- 无命令在途时 VT 线程阻塞在 `recv_timeout(50ms)` 里，查询在通道里排队，
  直到节拍到点才被应答。`types.rs` 的 `VT_IDLE_TICK_MS` 注释早已写明这一事实：
  「VT 线程只在命令批尾与**本 tick 到点**时排空查询通道，故无命令在途时一次查询要
  等满整个 tick。」
- 渲染线程的 kitty 放置查询（`ffi.rs` 的 `take_kitty_placements_on`）走的正是这条路。

### 缺陷

每次查询的最坏延迟等于一个空闲节拍（50ms）。渲染线程刚收到单元数据帧——
VT 线程刚推完帧、正要进入下一次 `recv_timeout`——就发出查询，
查询必然等满一个节拍，于是该帧的 `render` 段多出 ~50ms。

真机 logcat 的证据与之吻合：`SLOW_RENDER_INNER` 的 `render` 段为 53–56ms，
而 `phase1` / `receive` / `lock` 均 ≈0；同一批日志里 `SLOW_RENDER_PHASE`
（GPU 提交/呈现段）与 `SLOW_CELL_BUILD`（单元构建段）**一次都没出现**
（两者的阈值同样是 30ms，且各自独立限频，首条必现）。
耗时既不在 GPU 段也不在单元构建段，只可能落在两者之间的 VT 查询往返上。

代码注释已记录同一现象：「滚动每一步都去 VT 线程同步查一次放置，会让渲染线程每行等一次
完整查询（真机 yazi 预览下实测每行约 60ms，滚动掉到 ~16fps）」——
但那只是「滚动时不查」的规避，没有消除应答延迟本身。

自动化判据同样缺失：查询用例只断言「在 `QUERY_TIMEOUT_MS`（500ms）内返回」，
而节拍（50ms）比它小一个数量级，用例全绿也掩盖了串行化。

### 决策

1. **双通道等待**：VT 线程用 `flume::Selector` 同时监听命令通道与查询通道，
   任一就绪即醒。查询就绪时立即取出并应答，连同通道里其余查询一并处理，
   不再等节拍。
2. **节拍职责收窄**：空闲节拍只保留它真正的职责——排空通道里**残留**的查询，
   以及在状态变化后推送单元数据。查询的应答不再依赖节拍。
3. **不缩短节拍**：节拍是「无命令时也要周期性推送单元数据」的兜底，
   把它从 50ms 缩到 5ms 只是把串行化变小（查询仍要等一拍），
   却让 VT 线程的空转频率上升 10 倍。
4. **查询通道断开后不再参与选择**：`flume::Selector` 对已断开的通道恒为就绪，
   继续选择它会变成忙等。

### 备选与否决理由

- **把查询并入命令通道**：查询与命令共用 1024 容量，PTY 高压时查询会被命令积压挤掉
  并直接回退兜底值——比等待更糟；且会改变「命令先发即先生效」的顺序语义。
- **渲染线程改用缓存**：kitty 放置本来就只在失效条件命中时才查，
  问题不在查询频率而在应答延迟；缓存化会把一致性问题挪到别处。

### 判据

- 新用例 `idle_vt_thread_answers_queries_without_waiting_for_tick`：
  空闲 VT 线程上连续 8 次查询的总耗时应小于两个空闲节拍（100ms）。
  修复前实测 **383.87ms**（≈8 × 48ms，每轮各等满一拍），修复后应 < 5ms。
- 既有查询用例（标题、回滚长度、选中文本、搜索）行为不变，全部保持通过。
