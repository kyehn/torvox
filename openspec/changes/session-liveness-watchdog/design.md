# 设计

## 背景与现状

当前会话挂起的可观测面只有 `RenderWatchDog`：

- 它以 `entry.frameMarks`（`startNanos` / `doneNanos`）为输入，每 2s 检查一次。
- 判定条件是 `startNanos > doneNanos` 且空闲超过 10s 且 `isRunning()` 为真。
- 命中后只把 `entry.renderThreadExited` 置真，由 `checkSessions` 以指数退避重启渲染线程。

这条路径有两个盲区：

1. **层级盲区**：`frameMarks.startNanos > doneNanos` 只说明“整帧没跑完”，不能区分是
   渲染线程卡在 `bridge.render()`、`pollAll()`、还是 Kotlin 侧事件派发；VT 线程的停滞
   完全不可见。
2. **恢复盲区**：渲染线程重启不能解决 VT 线程挂起；若挂起发生在原生侧，重启渲染线程
   只是反复把挂起会话判死，最终 `closeDeadSession` 关掉用户的 shell。

现有代码已经具备部分基础：

- `RenderWake` 是“代数 + Condvar”的事件唤醒，输出到达与 Kotlin 信号共用它。
- `SessionEntry` 持有 `render_wake`、`new_output`、`alt_screen_active` 等原子镜像，
  渲染线程不必取会话锁即可读取关键状态。
- `Session::take_reported_exit` 已把“退出码到手才上报”作为不变量，避免伪造 0。
- `join_with_timeout` 已为线程回收提供有界等待，避免拆卸被阻塞。

因此改进应复用这些机制，而不是另起一套线程模型。

## 设计目标

1. **可定位**：挂起时能报告层级（渲染 / VT / 输出投递 / Kotlin 生命周期）与挂起起点，
   而不是只给出一个布尔“挂了”。
2. **可恢复**：渲染层挂起可重建渲染线程；VT 层挂起必须关闭会话，不能只重启渲染线程。
3. **不破坏不变量**：PTY 字节一致性、背压、退出上报、会话锁纪律保持不变。
4. **可观测**：诊断信息进入现有日志与会话表，不引入新权限、通知或后台服务。
5. **可测试**：层级判定与恢复决策必须是纯函数，可 JVM/Rust 单测。

## 分层存活模型

### 判据前提：空闲不是挂起

“一段时间没有进展”本身**不构成挂起**：空闲 shell 的子进程不输出，PTY 读取线程阻塞在
`read()`，VT 线程阻塞在通道等待上，两者都不推进任何计数。若把「计数未推进」当作挂起
证据，每个空闲超过阈值的 shell 都会被判死——这比原缺陷更严重。

故判定的 MUST 以「有工作在途」为前提：在途工作由各层自己的**忙标记**给出，而不是由
「计数未推进」反推。忙标记只表达「此刻正在做某件事」，不表达「多久没做事」。

### 忙标记

| 层级 | 忙标记 | 置位时机 | 清零时机 | 含义 |
| --- | --- | --- | --- | --- |
| 渲染 | `frameMarks.startNanos > doneNanos`（既有） | 帧开始 | 帧结束 | 整帧未跑完 |
| VT | `vtBusySinceNanos != 0` | 开始处理命令批 | 批处理结束、回到通道等待 | VT 线程正在执行命令 |
| 输出投递 | `ptySendSinceNanos != 0` | 读取线程拿到数据并开始投递通道 | 投递完成 | 输出已读出但尚未交给 VT |

两个原生忙标记都是「自忙起时刻」而非代数：挂起时计数不再推进，只有起点仍有意义。
它们是原子量，渲染线程与看门狗只读，不取会话锁。

### 忙标记的时钟域必须留在原生侧

忙标记存的是**原生单调时钟**的读数（自进程内某个基准起算），而宿主语言的
`System.nanoTime()` 基准是另一个原点。两者跨边界相减得到的「时长」没有意义——
差值可能是天文数字，也可能是负数。

故 JNI 导出 MUST 已经换算成**已忙时长**（`now - marker`），宿主只拿到一个时长再
与阈值比较。已忙时长为 0 MUST 当且仅当标记未置位：刚置位的标记也 MUST 给出正值，
否则「忙」与「空闲」在导出值上重合。

### 为什么没有「PTY 读取层」

PTY 读取线程在无输出时阻塞于 `read()`，与「读取线程卡死」在进程内**没有可观测差别**：
两者都不推进计数、不持有任何在途工作。故不能把「一段时间没有读取代数」判成读取层
挂起。

读取侧真正可观测的阻塞只有一种：拿到数据却投不进通道（通道满）。此时
`ptySendSinceNanos` 非零并持续增长，而下游要么正忙、要么已不再消费——归因指向 VT 层，
不是读取线程本身。故层级表里没有「PTY 读取层」，只有「输出投递阻塞」，且其恢复动作
与 VT 层相同。

### 层级判定

看门狗每 2s 读取三个忙标记与渲染帧标记，按以下顺序判定，命中即止：

1. 渲染帧在途且距起点超过 10s → **渲染层挂起**。
2. `vtBusySinceNanos` 非零且距今超过 15s → **VT 层挂起**。
3. `ptySendSinceNanos` 非零且距今超过 20s → **输出投递阻塞**。
4. 渲染线程已死（或从未启动）而会话仍处于 running → **Kotlin 生命周期层挂起**。
5. 其余 → **正常**（含空闲会话）。

阈值差异的理由：VT 批处理有 4ms 时长预算与 64 条上限，单条命令执行超过 15s 即异常；
输出投递的 20s 上限覆盖通道满时的正常背压窗口（PTY 读取线程本就阻塞在投递上）。

### 恢复策略

| 层级 | 动作 | 理由 |
| --- | --- | --- |
| 渲染 | 重启渲染线程（既有路径） | 渲染线程无状态，重启代价最低 |
| VT | 关闭会话 | VT 状态在 Rust 侧持有，无法安全热重建；关闭后由用户新建 |
| 输出投递阻塞 | 同 VT | 归因下游未消费，重启渲染线程无效 |
| 生命周期 | 只记录，不自动处理 | Activity 重建、切后台期间不得误杀用户的 shell |

关闭会话沿用既有 `closeDeadSession` 路径：会话对用户呈现为“已结束”，由用户新建，
**不静默重建**——静默重建会丢掉用户的 shell 状态（工作目录、后台任务、已输入内容），
比停在原地更糟。

同一会话在 60s 内最多自动关闭一次（渲染层重启沿用既有退避与次数上限），避免恢复
风暴：反复关闭又新建的会话会让用户看到会话号乱跳。

## 诊断信息

`SessionLivenessDiagnosis`（Kotlin 侧）：

```kotlin
data class SessionLivenessDiagnosis(val hungLayer: HungLayer?, val busyNanos: Long)
```

- `hungLayer == null` 表示未挂起（含空闲会话）。
- `busyNanos` 是命中那一层的**已忙时长**（不是挂起起点）：原生侧换算好的时长，
  跨语言边界不存在「起点」这一可比较的量。
- 诊断信息只在判定为挂起时更新，空闲会话不产生任何噪声。
- 看门狗每 2s 判定一次；判定为挂起时才记日志，挂起期间日志随判定节拍产生。

## 落盘位置

### Rust 侧

- VT 线程：开始处理命令批前把单调时刻写入 `vtBusySinceNanos`，批处理结束后清零
  （回到通道等待即清零）。
- PTY 读取线程：开始向输出通道投递前写入 `ptySendSinceNanos`，投递完成后清零。
- 两个标记必须是原子量且**先写忙起点、后进入可能阻塞的区段**：先清零后干活会让
  看门狗在挂起瞬间读到 0 而漏判。
- JNI 导出把标记换算成已忙时长后交给宿主。

### Kotlin 侧

- 渲染线程：沿用既有 `frameMarks`。
- 看门狗：只读三个忙标记，不写入。

## 与现有机制的关系

- `RenderWake` 继续作为事件唤醒源，不被诊断逻辑替代。
- `RenderWatchDog` 保留，其 `onHangDetected` 改为“判定层级并交由会话管理器”，不再把
  渲染线程标死作为唯一动作。
- `checkSessions` 的重启逻辑只对渲染层挂起生效；VT 与输出投递阻塞走关闭会话路径。
- `RenderPauseLedger` 与后台/切前台逻辑不受影响：挂起诊断不参与暂停/恢复门控。

## 测试策略

- 纯函数：层级判定（给定三个忙标记与渲染帧标记，输出 `HungLayer?`）必须有 JVM 单测，
  覆盖正常空闲、渲染挂起、VT 挂起、输出投递阻塞、生命周期挂起五种情况，以及层级
  优先级（渲染层优先于 VT 层，VT 层优先于输出投递层）。
- 纯函数：恢复决策（给定 `HungLayer`，输出 `RestartRenderThread` / `CloseSession` /
  `RecordOnly`）必须有单测。
- 纯函数：关闭节流（给定上次关闭时刻，输出可否关闭）必须有单测。
- Rust 侧：忙标记的置位/清零顺序必须有单元测试（挂起中途读取必须看到非零起点）。
  判别力必须确定：VT 侧用「应答缓冲的互斥量」把 VT 线程卡在能力探测的代答上，
  输出投递侧用「填满有界通道」把投递卡在背压上——不靠 sleep 猜时序。
- Rust 侧：已忙时长的换算（空闲为 0、刚置位为正）必须有单元测试。
- 不得用 `@Ignore`、环境检查或跳过；缺少 Rust 产物时相关测试必须失败。

## 风险与缓解

- **误判空闲为挂起**：判据以忙标记为前提，空闲会话不命中任何一条规则；这是本设计
  与「按代数未推进判定」的根本差别。
- **误判正常背压为挂起**：输出投递阻塞的阈值取 20s，远大于通道满时的正常窗口。
- **诊断读取竞争**：忙标记是原子量，看门狗只读；VT 与读取线程各自只写自己的标记。
- **恢复风暴**：渲染层沿用既有指数退避与次数上限；关闭会话按 60s 节流。
- **真机差异**：阈值按现有 10s 渲染挂起经验设定，最终以真机 p95/p99 校准。

## 非目标

- 不实现进程级 watchdog 或整应用重启。
- 不改变 VT 引擎或 PTY 实现。
- 不新增用户可见的“健康度”UI，仅记录诊断。
- 不做「读取线程卡死」的判定：该状态在进程内不可观测，强行判定会误杀空闲 shell。
