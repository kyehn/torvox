# Design

## Context

渲染线程每帧走两条路径之一（`native/src/android/ffi.rs` 的 `render_inner`）：

- **新帧路径**：单元数据通道里有新帧 → 按内容差分算脏掩码 → 绘制。
- **空闲路径**：通道为空 → 用缓存帧（`last_frame`）重绘，门控条件是
  「搜索高亮变了 / 亚行余量变了 / 内容脏标志置位 / 累加器失效 / 需要整屏重绘」。

滚动事件的时序（Kotlin 渲染循环 → 原生 → VT 线程）：

1. 渲染线程调 `setScrollOffset`：把 `Command::ScrollViewport` 发给 VT 线程，
   **同时**把 `render_state.dirty` 置位。
2. 同一拍渲染线程调 `render()`：VT 线程多半还没处理滚动命令，通道为空 →
   走**空闲路径** → `dirty` 使门控放行 → 用**旧视口**的缓存帧重绘一帧。
3. VT 线程处理滚动命令 → 失效内容去重基线 → 推送滚动后的帧 → 唤醒渲染线程。
4. 渲染线程再走一次 `render()` → **新帧路径** → 呈现滚动后的内容。

于是一次滚动产生两次提交：第 2 步那帧既多余（内容未变）又错误（亚行余量已更新、
视口未更新，画出的内容比实际视口少滚整行数）。logcat 证据与之吻合：
采集窗口内 691 帧里 401 帧的实例数与前一帧完全相同，且 `bands=1`
（空闲路径只标了光标行）、`partial=false` 居多（余量变化 → 强制全量）。

`dirty` 置位是「内容去重会吞掉滚动重绘」时代的补丁：那时滚动后推的帧内容逐字节
相同，被 `push_cell_data` 的去重吞掉，屏幕停在滚动前的画面（用户报「滑动不动、
点一下才出」）。去重缺陷已修（滚动命令会置 `last_cell_data_push = None`，
强制推帧），补丁却留了下来。

## Goals / Non-Goals

**Goals:**

- 滚动命令在途期间不呈现陈旧帧：一次滚动事件只产生一次呈现帧提交。
- 不牺牲「滚动及时上屏」：滚动后的帧到达即呈现。

**Non-Goals:**

- 不改滚动的内容模型（视口偏移仍由 VT 线程的 `scroll_viewport` 施加）。
- 不改 vsync 合并策略（滚动入口仍只更新偏移，由帧回调统一唤醒）。
- 不处理 kitty 放置缓存、帧时长统计等旁支问题。

## Decisions

### 一、用「滚动命令在途」标志表达内容是否过期

渲染态新增一个布尔标志：滚动命令发出即置位，新帧就位后清除。空闲路径在该标志
为真时直接返回（不重绘）。

**备选与否决理由：**

- **让渲染线程同步等 VT 线程应答滚动**：违反「渲染循环不得阻塞等待」的既有约束
  （洪流期间会把帧拖到 PTY 输出的时长），且拖动滚动每步一次 RPC 不可接受。
- **让单元数据帧携带滚动代数（`CursorInfo` 加字段）**：能精确区分「这帧是否包含
  本次滚动」，但要求命令、代数、帧三处协议同时改；而 VT 线程在批处理中途推送的
  帧本就可能不含滚动，那一帧仍会被呈现，收益只覆盖「跳过陈旧帧」之外的竞态，
  代价却大得多。
- **Kotlin 侧在发出滚动的这一拍跳过 `render()`**：会一并跳过该拍的
  `new_output` 采样、surface 失效上报、备用屏上报等副作用，这些与滚动无关，
  不该被滚动带偏。

### 二、标志的清除点放在新帧路径

新帧到达即意味着屏幕内容反映了本次滚动（VT 线程处理滚动命令后才推帧），
故在新帧路径清标志。渲染失败时也清：那一帧的单元数据已存进 `last_frame`，
由 `dirty` 标志触发空闲重绘重试——若标志不清，重试会被空闲路径自己挡掉。

**残留竞态**：VT 线程正在处理一批输出时滚动命令才入队，那一批推的帧不含滚动。
该帧到达会清掉标志，于是仍可能呈现一帧「旧视口 + 新余量」。这只在滚动与 PTY
输出同时发生时出现，且下一帧即被滚动后的帧纠正——与修复前同阶，不构成回退。

### 三、空闲重绘门控抽成纯函数并补表驱动单测

门控判定（五个变化信号 + 滚动在途）抽成纯函数，单测以判定表覆盖：
「滚动在途时无论其余信号如何都不重绘」与「其余信号任一为真即重绘」。

### 四、跳过时归还内容脏标志

内容脏标志（字体、字号、主题等改动的唯一触发点）在空闲路径里是读清即消费。
滚动在途而跳过时必须把它归还：那些改动只置此标志、没有别的触发点，
被这一帧消费掉就再也不会画出来。

## Risks / Trade-offs

- **滚动后的帧丢失 → 屏幕停在旧视口** → 帧丢失只可能发生在单元数据通道满时
  （容量远大于渲染线程一帧的消费量，稳态下通道至多积压一帧）；滚动命令已使
  去重基线失效，下一次推送仍会补发该内容。标志随之清除，屏幕恢复。
- **亚行余量生效晚一帧** → 余量与滚动后的新帧一并生效，视觉上是一次整体位移，
  比先错位一帧再纠正更稳。
- **空闲重绘被推迟** → 滚动在途期间搜索高亮等改动由随后的新帧一并呈现
  （新帧路径本就按当前高亮绘制），不丢内容。
