# Design

## Context

应用的目标 SDK 是 28，低于平台把文本提示改为「系统渲染」的门槛（R）。故 `Toast.makeText`
在应用进程里被渲染成一个真正的窗口，平台只负责排队与计时。三条平台约束随之而来：

1. 同一 UID 同时只允许一个提示窗口：连发两条时第二条抛 `BadTokenException`。
2. 窗口到期摘除时，平台已把该提示移出队列；应用随后回报令牌得到 `Toast already killed`。
   提示已到期后再取消它则得到 `Toast already cancelled`。这两条是窗口生命周期的必然结果，
   靠「先取消再展示」只能消掉第 1 条。
3. 平台按包限额提示频率。应用不在前台时限额生效，超额的那条被直接丢弃并打出
   `above allowed toast quota`——用户看不到反馈。

三条约束都指向同一个结论：应用内反馈不该借用系统窗口。

## Goals / Non-Goals

**Goals:**

- 应用内瞬时提示不再产生任何平台侧 W 级条目。
- 提示不再被平台丢弃：连续操作时每条反馈都看得见。

**Non-Goals:**

- 不改后台桌面通知的投递方式：前台提示与后台系统通知是两条路径，后者已走系统通知。
- 不引入新的依赖：呈现通道用现成的 Material3 `Snackbar`。

## Decisions

- 提示由应用内通道承载：`TransientMessageChannel` 是一条 `SharedFlow`，界面层订阅它并以
  `Snackbar` 呈现。通道无窗口，不受平台的窗口独占与按包限额约束。
- 通道由 `TerminalViewModel` 持有：终端页与设置页都经同一个 ViewModel 取通道，字体与清除
  数据两条业务路径也由 ViewModel 转递消息，故通道的生命周期与界面同在一个作用域里。
- 通道 replay 为 0：没有界面时消息直接丢弃，不排队补发。补发一条过时反馈比不反馈更糟。
- 终端页在设置页打开时停止订阅：两层界面同时在场时同一条消息会被呈现两次。设置页在场时
  由设置页呈现，终端页的提示条在设置页之下，也就不会与设置页的提示重复。
- 新的提示替换当前提示：呈现前先撤下当前那条，连切字体时不会排出一列旧反馈。
- 投递点保留在业务侧：`FontManager` 与 `TerminalViewModel` 仍在自己判定出结果的地方投递，
  呈现方式由界面层决定。投递不需要主线程——通道是线程安全的，界面层的订阅者在主线程收。

## Risks / Trade-offs

- [Snackbar 与平台提示的外观不同] → Snackbar 取应用自己的 Material3 配色，与界面同源；
  平台提示取系统样式，反而与应用主题不一致。
- [Snackbar 覆盖终端底部] → 提示条贴在键栏之上，不遮挡按键；终端内容本身不被推移。
- [设置页打开时终端页不再订阅] → 该窗口内若有提示由设置页呈现；两层界面不会同时呈现同一条。
