# Design

## Context

渲染状态 `RENDER_STATE` 是一把全局互斥锁，渲染线程每帧取两次（阶段 1 准备、阶段 3
绘制），JNI 的各条设置入口也取它。锁的临界区里做的事越重，终端冻结越久。

字体族索引 `font_db::family_index` 是进程级 `OnceLock` 缓存：族名只存在于字体文件的
name 表里，要把 `fonts.xml` 声明的每个文件读一遍才能得到，故真机一次 127ms。索引
本身与渲染状态无关——它既不读渲染字体库，也不写。

现状把这次 127ms 放进了锁里：

| 入口 | 持锁期间做的事 | 后果 |
| --- | --- | --- |
| `listFontFamilies` | `font_pipeline.list_monospace_fonts()` → `family_index()` | 打开字体选择器时终端冻结 127ms |
| `setFontFamily` | `font_pipeline.set_font_family()` → `load_family()` → `family_files()` → `family_index()` | 应用已存字体族（会话启动）或从列表选族时终端冻结 127ms |

`loadFontFile` 已在上一变更里摘掉了族枚举（族已知，直接装库），故它不是本变更的
对象；但它必须继续不触发枚举——这要求「族已在库中」有一条不碰族索引的快径。

## Goals / Non-Goals

- Goal：族索引的构建 MUST NOT 发生在渲染状态锁内。
- Goal：按需装入族时，锁内只剩「把该族的文件装进渲染字体库」这一件事。
- Goal：族已在渲染字体库中时不解析族文件列表（常驻三族、用户选文件装入的面）。
- Non-goal：不改族索引的内容、顺序与去重规则。
- Non-goal：不改渲染状态锁的粒度。字形重光栅（换字号、换字体族时的整库重光栅，
  约 15ms）仍在锁内——它改的是渲染字体库本身，挪出锁需要把管线拆成独立对象，
  代价远大于收益。
- Non-goal：不改「按需装入族」这条链路本身：设置页从列表选中的族仍经
  `load_family_files` 装入。

## Decisions

### 决策一：族索引在锁外构建

族索引是进程级缓存，与渲染状态无读写关系。把它挪到锁外不需要任何状态协调：
`OnceLock` 保证并发调用只构建一次，其余调用者等待同一个结果。

`listFontFamilies` 因此不再持有渲染状态锁取列表（Android）。宿主构建没有族索引，
列表取自渲染字体库，仍须持锁——两条路径的差别用 `cfg` 显式分开，不做隐式回退。

### 决策二：`setFontFamily` 两段式

族文件列表（`family_files`）的解析可能触发族索引构建，必须在锁外；而「把这个族
装进渲染字体库」要改管线，必须在锁内。故拆成三步：

1. 持锁：`family_resident(family)` 判定族是否已在渲染字体库中。
2. 解锁：缺族时解析族文件列表（`family_files`）——可能首次构建族索引。
3. 重新持锁：装入族文件（`load_family_files`）并选中。

族已在库中时第 2 步整个跳过：常驻三族与用户选文件装入的面都命中这条快径，
「装载字体文件不触发族枚举」的要求由它守住（`loadFontFile` 走的就是这条快径）。

- 备选「先在锁外无条件解析族文件列表」：常驻三族（会话启动时的系统等宽字体）
  也会触发 127ms 枚举，且违反「只启动终端不做字体设置时 `FONT_INDEX` 不出现」。
- 备选「把族索引构建挪到后台线程」：族索引的构建时机由规范定为「显示列表时」，
  后台预热既改时机又改语义，还多一条线程与生命周期。
- 备选「渲染线程改用 `try_lock`，拿不到锁就跳帧」：跳帧与冻结在观感上等价（终端
  画面同样停 127ms），却把一处可修的持锁区间换成全渲染路径的丢帧策略。

### 决策三：装入与解析分成两个函数

`font_db::load_family(db, family)` 把「解析族文件列表」与「装入族文件」揉在一起，
调用方无法把前者挪出锁。拆成 `family_files(family)`（纯查询，可能构建索引）与
`load_family_files(db, files)`（只装入）后，锁的边界由调用方显式划出。

宿主构建的字体库已含系统全部字体，没有族索引也没有按需装入：`family_files` 在宿主
构建下恒为 `None`，`load_family_files` 不参与编译。

### 决策四：管线接口显式接受族文件列表

`FontPipeline::set_font_family(family, family_files)` 不再自行解析族文件列表。管线
住在渲染状态里，它自己解析就等于在锁内解析；把列表交给调用方，锁的边界才由调用方
决定。

`family_resident` 与 `set_font_family` 的取面顺序保持一致（用户选文件装入的面优先，
其次按族名扫库），否则「判定为常驻却选不中」会出现。

## Risks / Trade-offs

- [两段式持锁之间族的状态可能变化] → 第 2 步只读族索引（进程级缓存），不碰渲染
  字体库；第 3 步重新判定并在缺族时装入。`loadFontFile` 在此期间装入同一个族也安全：
  fontdb 的 `load_font_file` 对已装入的源是幂等的。
- [锁的往返从一次变两次] → 第二次取锁前没有任何持锁操作，锁的竞争面不比原来大。
- [宿主构建多出一个 `family_files` 桩] → 它让 JNI 层不必按平台分叉，桩恒返回
  `None`，与宿主构建「字体库已含全部系统字体」的事实一致。
- [Android 专属路径无法在宿主跑单测] → 锁的边界由代码结构保证（族文件解析出现在
  取锁之前），行为由管线层用例钉住（`family_resident` 的判定口径、
  `set_font_family` 的取面顺序）。
