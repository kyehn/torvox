# Design

## Context

采集窗口 84s，应用自身 1770 条日志。逐帧诊断的形态：

- **原生侧「已呈现」**：`native/src/render/pass.rs` 在每次 GPU 呈现后打一行
  `render_frame: presented N instances (partial=…, bands=…)`。691 行，间隔中位
  15ms——即每帧一行。这条日志是唯一的「GPU 真的呈现了」信号（宿主侧的
  `count > 0` 只表示「本帧有新内容可画」，空闲重绘不计入）。
- **原生侧滚动落点**：`native/src/android/ffi.rs` 的 `setScrollOffset` 每次
  滚动偏移变化打一行，222 行，间隔中位 24ms——手势期间与逐帧同频。
- **宿主侧帧节奏窗口**：`FrameTimingStats` 按「60 帧或 2s」收口，出两行
  （渲染耗时、整循环耗时）。相邻间隔出现 492ms：60 帧在 122Hz 的设备上只要
  492ms，低于规范要求的 500ms 下限。

规范（`logcat-hygiene`）对这些的要求：

- 「同一会话内两次输出之间的间隔 MUST 不小于 500ms；MUST NOT 以逐帧频率刷屏」
- 「限频 MUST NOT 吞掉升级信号：同一状况的累计计数与阈值告警 MUST 照常输出」
- 「诊断的价值在于形状（次数、分布、阶段占比），不在于条数」

## Goals / Non-Goals

**Goals:**

- 逐帧诊断的输出间隔不小于 500ms，且不丢计数。
- 汇总行读起来不含歧义：`partial` 与脏带数各说各的。
- 热路径的值落点只留 trace，不占日志通道。
- 帧节奏报告的间隔下限在任意帧率下都成立。

**Non-Goals:**

- 不改渲染管线的行为（本次不动一帧一格的绘制逻辑）。
- 不改仪器化用例的判定口径（滚动期的节奏门限、帧率门限都不动）。
- 不动 `FONT_XML` 解析（已由既有的「每进程解析一次 + 跳过项汇总」修掉）。

## Decisions

### 一、逐帧呈现诊断按窗口汇总，而不是逐帧丢弃

`SlowLogThrottle` 已有的语义是「两次放行之间至少间隔 500ms」。直接拿它限频
只能丢掉中间的行——窗口内呈现了多少帧就此不可见，排障时看不出「多久一帧」。
故新增带计数的闸门：每次呈现累加计数，闸门放行时把计数连同末帧形态一起输出。

一行汇总同时给出「窗口内帧数」（可反推帧率）与「末帧形态」（实例数、是否部分
帧、脏带数），条数降到原来的约四分之一，信息不减。

**备选与否决理由：**

- **整条删掉**：仪器（`ScrollBehaviorQuantifiedTest`）靠这条日志判断滚动期
  是否真的呈现了帧，删掉后该断言失去依据；渲染期的帧率也无从反推。
- **降到 trace**：Android 端 logger 的上限是 `Debug`，trace 一律被过滤
  （`native/src/android/logging.rs`），日志从此不可见——比降噪更糟。
- **保持逐帧、只调级别**：同上。

### 二、汇总闸门挂在渲染器上

`Renderer` 是全局单例（`RENDER_STATE` 里唯一一份），但同一时刻只渲染当前会话
（`DESIGN.md`「只渲染当前使用的会话」），故计数器在会话切换时最多多算一次切换
前后的帧。比起在会话表里另挂一份计数器，这个差异不影响任何判定。

闸门复用 `slow_log` 模块既有的 500ms 下限常量，不另立标准。

### 三、滚动偏移落点降为 trace

`setScrollOffset` 与 `setScrollYPx` 是同一条手势路径上的两个落点：前者在偏移
变化时打一行，后者在像素余量变化时打一行，频率同为「每次手势 MOVE 一次」。
后者已经是 trace（注释写明「debug 级只会把 CI 日志刷满」），前者留在 debug 是
分级上的矛盾。

滚动偏移的值本身没有诊断价值——偏移错了在画面上立刻可见，而它的落点既不是
性能信号也不是告警信号。故降为 trace：本地需要时临时放开日志级别即可，
默认不占日志通道。

### 四、帧节奏窗口：环形覆盖 + 延后出报告

`FrameTimingStats` 的窗口是「60 帧或 2s」，定长数组按帧写入、满即结算。
要保证输出间隔不小于 500ms，只有三条路：

1. **窗口攒满即结算、过早的报告丢掉**：简单，但 122Hz 以上的设备上会丢掉
   一半的统计样本，报告只描述了一半时间线。
2. **窗口改成纯时间窗（500ms 或 2s）**：固定容量数组与时间窗互斥——120Hz 以上
   的设备上 500ms 内的帧数超过 60，样本放不下；把容量放大到覆盖最坏帧率则
   要为「2s × 240Hz」留 480 个槽位，且 60 帧的统计口径被时间改写。
3. **样本环形覆盖、报告延后给出**：窗口满后新帧覆盖最旧样本，报告在间隔下限
   满足时给出。统计保留最近的 60 帧，输出间隔恒不小于 500ms。

选第三条。代价是「窗口攒满但未结算」成为常态，原先那条「越过满窗口仍来记录」
的 error 告警（防止数组越界抛异常）不再适用：数组越界由写入位置取模保证，
告警改为「窗口已满且迟迟不出报告」——那才是调用方不再取报告的缺陷。

### 五、汇总行里的 `bands` 改称 `dirty_bands`

该值是脏带数（脏行按单元格高度合并成的带），全量帧也会打印：空闲路径只标
光标行，故全量帧常见 `bands=1`。它与 `partial`（本帧是否走部分路径）是两件事，
原来紧挨着写，读起来像「部分帧只画了 1 条带」。改名后语义自明。

## Risks / Trade-offs

- **汇总行不再逐帧可数**：帧率改由「窗口内帧数」反推（500ms 窗口下 30 帧
  即 60fps），精度足够；逐帧计数在排障时本就不可靠（采样间隔不均）。
- **延后出的报告描述的是最近的 60 帧而非窗口起始的 60 帧**：统计量（均值、
  p95、最大）与顺序无关，覆盖最新的样本更贴近当下。
- **环形覆盖丢掉窗口起始的样本**：只在间隔未到时发生（快设备），丢的是更旧的
  样本，保留的是最新的——方向正确。
- **trace 级日志默认不可见**：滚动偏移的逐次落点不再出现在 logcat。画面上的
  偏移错误仍会立刻暴露，需要逐次数值时临时放开日志级别。
