# 设计

## 现状与根因

规范对限频诊断的要求有两层：按窗口输出（每窗口至多一行），以及行内带上窗口内
的事件计数。事件队列与桌面通知队列的溢出告警只满足前一半。

两处都用 `slow_log::SlowLogThrottle::should_log()`：放行时输出一次，窗口内的命中
直接丢弃，行内也没有次数字段。同一份规范下，命令入队失败、剪贴板队列溢出、VT
应答队列溢出三处已用 `CountedLogThrottle`（窗口内计数随那一行交出），形成两种
做法。

缺口落在最需要形状的两处：两队列都处在可被程序洪泛的路径上——事件队列由 PTY
输出驱动（远端可无界地循环 OSC 52 读请求），桌面通知队列由 OSC 9 / OSC 777
通知驱动。洪泛时「丢了多少条」正是判断影响面的依据。

## 方案

两处都改用既有的 `slow_log::CountedLogThrottle`：记一次事件，闸门放行时交出窗口
内累计的事件数，窗口内则继续攒着。无需另造统计口径。

静默期保持各队列原有的 1s（`OVERFLOW_WARN_INTERVAL_MS`），而逐帧诊断的默认窗口
是 500ms。差异 MUST 体现为闸门的配置，故 `CountedLogThrottle` 补一个与
`SlowLogThrottle::with_interval` 同形的 `with_interval`，而非另写一份私有闸门。

字段命名：事件队列的行内字段取名 `dropped_events`，桌面通知队列取名
`dropped_notifications`。规范要求同一行的各字段以自身名称标识，两者不得互相
冒充。

事件队列有两类丢弃：淘汰最旧的一条（记事件种类与会话 ID）与丢弃新来的事件
（队列只剩受保护事件时）。二者共用一把闸门，计的是同一件事——窗口内一共丢了
多少条事件，故两类行都给出同一个 `dropped_events` 计数。

## 取舍

- 不改告警的分级：队列溢出仍是 warn——它意味着程序洪泛或消费侧跟不上，是真实
  的异常，不是正常退化。
- 不改丢弃策略：事件队列仍保 `Exit` 与 `ClipboardRead`，通知队列仍丢最旧。
- 计数以 `u32` 累加并饱和，不会因洪泛而回绕成小数字。

## 验证

- 回归用例：事件队列与桌面通知队列各自断言「首条丢弃即交出、其后攒在窗口里」。
- `cargo test --lib`、`cargo clippy --all-targets -- -D warnings`、`cargo fmt --check`。
