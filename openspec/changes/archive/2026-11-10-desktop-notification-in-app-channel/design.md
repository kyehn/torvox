# Design

## Context

桌面通知（OSC 9 / OSC 777）的前台呈现仍借用平台提示窗口。应用的目标 SDK 是 28，低于平台把文本
提示改为「系统渲染」的门槛（R），故 `Toast` 在应用进程里被渲染成真正的窗口，平台只负责排队与计时。
三条平台约束随之全部落在应用身上：

1. 同一 UID 同时只允许一个提示窗口：连发两条时第二条抛 `BadTokenException`。
2. 窗口到期摘除时平台已把该提示移出队列，应用随后回报令牌得到 `Toast already killed`；提示已到期
   后再取消它则得到 `Toast already cancelled`。每条到期的提示都会留下平台侧条目。
3. 平台按包限额提示频率。应用不在前台时限额生效，超额的那条被直接丢弃并打出
   `above allowed toast quota`——用户看不到反馈。

上一轮已把应用内的其余瞬时提示改走应用内通道（`TransientMessageChannel` + Snackbar），树内只剩
桌面通知这一处平台提示窗口。

## Goals / Non-Goals

**Goals:**

- 树内不再有平台提示窗口的调用点：前台桌面通知也不再产生平台侧 W 级条目。
- 前台桌面通知与应用内的其余提示共用一条呈现通道，呈现口径一致。

**Non-Goals:**

- 不改后台桌面通知的投递方式：后台仍走系统通知，点击切回目标会话的行为不变。
- 不改通知的文本口径：会话序号前缀与标题、正文的拼接口径不变。

## Decisions

- 前台桌面通知经 `TransientMessageChannel` 投递：通道无窗口，不受平台的窗口独占、窗口生命周期
  与按包限额约束。呈现形态与前台的其余提示一致，都是应用自己的 Snackbar。
- 通道改为依赖注入提供的进程内单例：桌面通知由运行期投递，提示由界面层呈现，两处若各持一份通道
  就会分叉——投递到无人订阅的通道等于丢弃。
- 前后台判据不变：仍取 Activity 生命周期（`MainActivity` 的 onStart/onStop），不改成「渲染是否
  暂停」。设置页在场时用户仍看着应用，前台路径照样成立。
- 保留 `DesktopNotificationPlayer` 的动作注入点：单测直接验证「前台走应用内提示、后台走系统
  通知」与文本口径，不必伪造系统服务。
- 前台路径不再需要主线程切换：平台提示窗口的构造要求 Looper，应用内通道是线程安全的，投递点
  随之简化。

## Risks / Trade-offs

- [Snackbar 与平台提示的外观不同] → 与应用内的其余提示同源，都是 Material3 的 Snackbar，不再有
  一半提示走应用主题、一半走系统样式。
- [前台桌面通知不再悬浮在应用之上] → Snackbar 贴在键栏之上，不遮挡按键；用户仍能立刻看到通知。
- [规范文档措辞过时] → `docs/specification/DESIGN.md` 仍写「应用位于前台时使用 Toast Notification」。
  该文件受保护，须经用户同意后方可修改，本变更不改它。
- [应用内提示在后台不可见] → 后台仍走系统通知，判据与行为均未改变。
