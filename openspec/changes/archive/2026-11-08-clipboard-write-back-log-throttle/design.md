# 设计

## 现状与根因

`handle_clipboard_reads` 有两条回写路径：洪泛削减分支就地作答空串，正常分支由
应答线程把宿主答复写回 PTY。两条路径的回写失败都经 `log_clipboard_write_back_failure`
逐次记一行 `warn`。

逐次输出在洪泛削减分支上是常态而非例外：该分支按帧封顶（每帧最多 16 次回写），
而每次回写都可能因 PTY 写超时而失败——子进程不读 stdin 时，失败率接近 100%。
一帧 16 行 warn、每秒近千行，`logcat-hygiene` 的「逐帧诊断 MUST 以时间窗口汇总
输出」正是为这种形态而设。

## 方案

复用既有的 `slow_log::CountedLogThrottle`：它已用于剪贴板写入队列溢出、VT 应答
队列溢出与终端命令入队失败三处，语义是「记一次事件；闸门放行时交出窗口内累计的
事件数，窗口内则继续攒着」，正好满足规范里「报告延后而不是丢弃」与「行内带上
窗口内的事件计数」两条要求。

闸门取进程级静态量，与同处的洪泛削减闸门（`FLOOD_SHED_WARN_THROTTLE`）同口径：
两者描述的是同一次洪泛事件的前后两半，共用一把闸门可让一次洪泛在 logcat 里留下
一条汇总行，而不是两把闸门各留一行。

会话已结束的判定留在闸门之外：该情形是正常退化路径（会话已退出，或 PTY 已随
子进程关闭），记 debug 且不计入失败窗口——否则每次会话收尾都会在下一条真实失败
的行里多带一个虚假的次数。

## 取舍

- 分级维持 `warn`：回写失败意味着远端的剪贴板读请求得不到答复，是真实异常。
  限频不降级，只把「逐条」改为「按窗口」。
- 失败文本只带最后一个错误：窗口内的错误可能各不相同，逐条列出会让汇总行重新
  膨胀成洪水；最后一个错误足以说明失败性质，次数足以说明规模。

## 验证

- 单测：首条失败立即交出窗口计数（不得被限频吞掉）；窗口内的失败攒在闸门里，
  下次放行时一并交出；会话已结束不计入失败窗口。
- `cargo test --lib`、`cargo clippy --all-targets -- -D warnings`、`cargo fmt --check`。
