# 设计

## 现状与根因

`Session::drain_pty_write_back` 每帧收割 VT 应答：队列超出上限 256 条时丢
最旧，并逐帧记一行 `error`。

逐帧命中不是理论情形：子进程不读 stdin（典型是程序卡在等应答）时，每帧的
`drain_pty_write_responses` 仍会补进新应答，队列稳定在上限之上，溢出逐帧发生。
一条 error 每帧一次，60fps 下即每秒 60 行——`logcat-hygiene` 的「逐帧诊断
MUST 以时间窗口汇总输出」正是为这种形态而设。

## 方案

复用既有的 `slow_log::CountedLogThrottle`：它已经在剪贴板写入队列溢出与
终端命令入队失败两条路径上使用，语义是「记一次事件；闸门放行时交出窗口内
累计的事件数，窗口内则继续攒着」，正好满足规范里「报告延后而不是丢弃」与
「行内带上窗口内的事件计数」两条要求。

队列裁剪与计数记入收敛到一个函数：它同时做「算出超量、丢最旧、把条数记进
闸门」三件事，并把闸门交出的窗口计数返回给调用方输出。这样该口径不依赖
日志捕获即可被用例直接断言——否则只能靠「观察 logcat 有几行」来验证限频，
既不可复现也不精确。

## 取舍

- 分级维持 `error`：丢弃应答意味着子程序的设备状态查询永远得不到回答，属
  真实异常。限频不降级，只把「逐条」改为「按窗口」，升级信号因此保留。
- 告警文本不再带队列总深度：窗口汇总后，深度是窗口内某一时刻的瞬时值，
  与累计条数不同源，带上反而误导。累计条数已足够定位丢弃规模。

## 验证

- 单测：首条必可见且带本窗口条数；窗口内再次溢出不再输出第二行；窗口内的
  条数攒在闸门里，下次放行时一并交出。
- `cargo test --lib`、`cargo clippy --all-targets -- -D warnings`、`cargo fmt --check`。
