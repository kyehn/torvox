# Proposal

## Why

字体回退链在**合成运行**（粗体/斜体）下逐帧重走，而链上的两处查表都没有缓存：

- 「面 → 字形号」查表每次都重入 `with_face_data`，把字体文件重新 mmap 并重建
  charmap。合成路径跳过 `cjk_glyph_cache`（该缓存记的是常规样式的解析结论），
  于是每帧每字都要重做一次查表。
- 「库内无面能解析此码位」的负缓存只在常规样式下写入，合成样式下不写，于是
  粗体/斜体文本里的罕见码位每帧都要遍历 fontdb 全部 face 重扫一次全库。

两条开销都落在**每帧每字**的路径上：终端里一段粗体中文或一个粗体的罕见汉字，
就足以把渲染帧拖慢。负缓存当初引入就是为了消掉「罕见汉字每帧一次」的开销，
但只覆盖了常规样式，合成样式把同一条开销又放了回来。

判别依据：样式面查表早已入缓存（`style_glyph_id_cache`，为样式面而设，键同为
「面 + 码位」），回退链却另起炉灶直接查表——同一件事被抄了两遍，其中一份
还漏了缓存。

## What Changes

- 样式面与 CJK 回退链共用同一个「面 → 字形号」缓存（键为「面 + 码位」），
  回退链不再逐帧重建 charmap。
- 「解析不出」的负缓存对合成样式同样生效：全库扫描的结论与样式无关。
- 不改渲染结果：查表口径与扫描判据都不变，只是把重复计算换成缓存命中。

## Capabilities

### New Capabilities

- 无

### Modified Capabilities

- `cjk-rendering`：补上回退链查表与负缓存在合成样式下的要求。

## Impact

- `native/src/render/font/**`：字体管线内部缓存与查表路径，产品可见行为不变。
- 不改 `docs/specification/`、`docs/STATUS.md` 等保护文件。
- 不引入新依赖，不 vendor 任何文件。
