# 提议：裁定 VT 上游缺口、按可用列数收敛字号上界、补齐文档提供者树 URI 契约

## 背景

用户报告三类症状「多次声称解决却依然存在」：字号调节条范围与实际可设范围不一致、
helix 等 TUI 应用在输入法弹出时内容被隐藏且回车变 `j`、documentsprovider 无法修改/
复制/移动文件；并要求解释 `72a33d33`（采纳 xterm.js vttest 派生语料 58 例）为何
添加大量测试文件却没有任何问题被报告。

## 已查明的事实

### 一、症状所在的构建与修复所在的构建不是同一个

`origin/kyehn-patch-1`（用户构建分支）与 `main` 的分叉点是 `b296c980`
（2026-10-06），该分支落后 `main` **198 个提交**。三个症状各自的修复提交
（回车 CR `fd46d6c4`、IME 平台 insets `ab8572f8`、位移 translationY `12dfa2d4`、
字号区间单一来源 `dddd67fa`、网格算式共用 `71333558`、字体变化重推光栅
`f333b22e`）经 `git merge-base --is-ancestor` 逐个验证**均不在**该分支上。

即：修复在 `main` 上真实存在，用户构建里没有。「声称解决」与「仍然存在」
分别对两份不同的代码成立。这是三轮反复的结构性根因：每轮的验证（`main` 上 CI
全绿、JVM 单测通过）从未覆盖用户实际构建的那份代码。

### 二、`72a33d33` 零问题报告的原因

该提交是**纯测试采纳**：58 例全部在当时就已通过（探针实测通过 58 例后才写断言），
因此「没有问题被报告」在算术上必然——它不宣称修好任何东西。

真正该被报告而未报告的是另外 **18 例不采纳**：它们全部实测失败，提交为每例写了
理由，但理由是**想定而非实测根因**。本轮逐个实测后订正：

| 语料 | 原理由（想定） | 实测根因 |
| --- | --- | --- |
| t0020/t0021/t0022/t0024/t0030/t0032/t0034 | 「本仓按标准取首参数」 | 整条序列被上游丢弃（`stream.zig` 写死 `params.len == 1`），光标一动不动 |
| t0081-TBC | 「语义尚未按标准裁定」 | `CSI g`（无参数）被上游整条丢弃；ECMA-48 规定 TBC 的 Ps 缺省为 0。显式 `CSI 0g` 本仓正确生效 |
| t0033-VPB_scroll | 「尚未按 DEC STD 070 裁定」 | 上游把 `k` 与 `A` 同等映射到 `cursor_up`，越过区域上边距不滚动 |
| t600/t601-SR/SL | 「同上」 | 上游对带中间字符的 `CSI A`/`CSI @` 直接 warn 后丢弃 |
| t602/t603-DECIC/DECDC | 「同上」 | 上游未实现 DEC 左右边距族，整条序列无分发 |
| t0060/t0061-DECSC | 「落点语义尚未裁定」 | DECSC/DECRC 行列还原正确；差异只在「光标处于 pending wrap 时一并还原了 wrap 标志」，xterm 只还原行列 |

## 方案

1. `native/tests/vt_upstream_blockers.rs`（新增）：以特征化断言逐个钉住上述缺口的
   当前行为，附标准要求与上游源码位置。它们不是正确性测试，而是「上游补齐即失败」
   的重新裁定触发器。
2. `SettingsRepository.fontSizeMaxSp` 增加第二条上界「至少 `MIN_USABLE_COLUMNS=20`
   列」：低于该列数一条常见命令（21 列）都放不下。与自适应默认字号共用同一个
   列↔字号比例；Termux 的 256px 上限保留为另一条约束，两者取紧。
3. DocumentsProvider 补树 URI 客户端契约覆盖（插桩 + JVM），含目录树复制/移动、
   冲突唯一名、链接 inode 语义、站外链接拒绝。

## 非目标

- 不打本地补丁适配上游 VT 缺口（DESIGN：跟踪上游 master，无本地补丁）。
- 不为让 18 例全绿而改期望值——语料内容必须原样才是外部真相。
