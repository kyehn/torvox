# Design

## Context

规范要求逐帧诊断限频，宿主侧已实现，原生侧未实现。本轮把原生侧补齐，并把限频的
语义（首条可见、时钟回跳不放行、每类独立计数、不得吞掉升级信号）写进规范。

原生侧慢帧诊断与取纹理告警都是「本帧异常即输出」的条件式日志：没有时间闸门时，
持续慢或持续失败就会变成逐帧刷屏。

## Goals / Non-Goals

Goals:

- 原生侧逐帧诊断与逐帧告警的两次输出间隔不小于 500ms。
- 首条诊断必须可见——第一次出现的慢帧往往就是最关键的那条。
- 每类诊断各自限频，互不吞掉。
- 升级信号（连续跳帧到上限记 error）不受限频影响。

Non-Goals:

- 不改变慢帧阈值（30ms，与宿主侧同档）。
- 不改变「慢」这件事本身的判定与恢复策略。
- 不给宿主侧已合规的诊断另起炉灶。
- 不改 `docs/specification/` 与 `docs/STATUS.md`（受保护文件）。

## Decisions

### 1. 限频闸门用「单调时钟 + CAS」

闸门保存上次放行时刻（进程启动以来的毫秒），放行条件是「距上次放行 ≥ 500ms」，
并用 CAS 推进窗口起点。

- 单调时钟而非墙上时钟：墙上时钟被校准时可能回跳，回跳会算出负间隔；
  本实现用 `Instant` 相对进程启动时刻的毫秒，天然免疫。
- CAS 而非「读—判断—写」：并发调用（多会话渲染线程）可能同时通过判断，
  同一时刻输出多行。CAS 保证只有一方推进窗口。

回跳按「未到窗口」处理（饱和减法得 0）：宁可少记，不误放——多记只是吵，
误放则是刷屏。

### 2. 每类诊断一个闸门

规范已有场景「慢循环与慢帧各自限频，MUST NOT 共用一个计数器而互相吞掉」。
同一原则延伸到全部八条诊断：渲染分段、单元构建、帧内分段、采样段、工作线程忙、
工作线程 panic、取纹理超时、尺寸不符，各持一个闸门。

代价是八个静态闸门；收益是任何一条诊断都不会因为另一条刚输出而被吞掉。

### 3. 静态闸门而非渲染态字段

渲染态是全局单例（`RENDER_STATE`），挂在它上面与静态等价，却要多改构造路径；
而 `render_inner` 这条 JNI 路径本就在全局渲染态之外。故统一用静态闸门，
与仓内既有的限频写法（静态原子量 + CAS）同款。

### 4. 限频不得吞掉升级信号

限频只作用于「逐帧诊断」这条输出路径，不作用于状态机：
连续跳过计数照旧逐帧推进，达到上限仍照旧记 error；取纹理超时仍逐帧重试。
即：被压住的是「同一条诊断的重复输出」，不是「判定本身」。

### 5. 首条必须可见

闸门以「尚未放行过」为初始状态，首条无条件放行。首条慢帧是排障时最有价值的信号，
且限频的目的是「不要刷屏」，不是「不要开口」。

## Risks / Trade-offs

- 限频会降低慢帧诊断的条数：持续慢时 500ms 一条，形状信息（分布）变粗。
  这是规范明确接受的取舍——「诊断的价值在于形状，不在于条数」。
- 静态闸门跨会话共享：多会话同时慢时，总输出速率上界为「类数 × 2 条/秒」，
  但任一类的相邻输出间隔仍不小于 500ms，满足规范。
- 时钟回跳（仅在用墙上时钟时才可能出现）在本实现中不存在；
  若将来改回墙上时钟，回跳会压住诊断而非放开，风险方向是安全的。

## Migration Plan

- 纯日志节流，无数据迁移、无配置开关、无行为变化（渲染与恢复路径不变）。
- 规范增量落 `specs/logcat-hygiene/spec.md`，归档时同步进主 spec。
- 回归判据：闸门单元测试（首条放行、窗口内压住、窗口走完放行、时钟回跳不放行）、
  Rust 全量单测、模拟器上滚动场景的输出间隔实测。
