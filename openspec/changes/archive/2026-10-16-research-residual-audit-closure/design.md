# Design

## Context

见 `proposal.md` — Why。此处只记录影响实现方式的三条约束。

1. **归档变更的 `tasks.md` 是历史事实记录，不是待办清单。** 改动它们等于改写
   已归档变更的历史描述，因此补勾必须带依据、且必须区分「本变更做的」与
   「后续变更做的」——虚记审阅轮次会把别人的工作记到自己账上。
2. **禁改区三项已由维护者裁定「都不改，只登记」。** 本变更对它们的唯一合法动作是
   把事实写进规范；对 `scripts/`、`.github/`、`android/app/build.gradle.kts`
   的任何写入都属于越权。
3. **上游归档自述与 git 事实可能不符。** `research-docs-retirement` 的 `tasks.md`
   写「先归档 ledger-closure，本变更后归档」，但 `git log --diff-filter=A` 显示
   两者在同一提交（提交标题「openspec: 归档 research ledger closure 与 research docs
   retirement 变更」）落地。登记 MUST 以 git 事实为准；按本仓
   `no-git-short-hash-in-source-and-docs` 规则，文档引用该提交 MUST 用提交标题
   等可解析坐标，MUST NOT 写短提交号。

## Goals / Non-Goals

**Goals:**

- 让全仓每一处 `- [ ]` 都能被读成三种明确状态之一：**已做且有证据**、
  **未做且写明原因与缺口性质**、**等他人在途动作**。MUST NOT 再留第四种
  「实际做了但忘了勾、且无任何线索指向谁做的」。
- 把禁改区三项从「只有落地方案」升级为「有实测基线 + 有验收判据」，
  使日后授权实施者不必重新调研基线。
- 尽最大可能闭合真机项：若宿主具备 KVM 与模拟器条件，就实跑而非以环境为由跳过。

**Non-Goals:**

- 不改任何运行期行为，不动 `native/` 与 `android/` 下的生产代码。
- 不实施禁改区三项（用户已裁定维持登记）。
- 不为 `research-residual-closure` 补造它自己从未执行的审阅轮次。

## Decisions

### D1：补勾采用「承接关系」而非「就近补记」

`2026-10-15-research-residual-closure` 第六节留白的三轮完整审阅，实为后续
`research-ledger-closure` 第五节与 `research-docs-retirement` 第三节承接执行。

- **选择**：在该处勾选，但正文写明「本变更未执行，承接方为 XXX 第 X 节」，
  并指向承接方的记录作为证据。
- **备选（否决）**：留空不管——留白正是本变更要消灭的东西。
- **备选（否决）**：直接把承接方的轮次改写成该变更自己做——这是篡改历史记录，
  且会让「哪一轮审阅发现了什么」这条证据链断在错误的位置。

### D2：真机项先探环境再决定闭合或维持缺口

`audit-research-residual-gaps` 的 5.4 记载「仪器测试需 Android 设备与 Vulkan，
本会话未执行」。但本宿主存在 `/dev/kvm`（`crw-rw-rw-`，非只读占位）、
`system-images/android-35/google_apis/x86_64` 已就位。

- **选择**：先实跑 `scripts/setup-emulator.nu` 探测；能起则实跑仪器测试并按实测
  闭合，不能起则把探测结果（KVM 可用、镜像就位、缺哪个组件）写入缺口说明，
  使缺口从「环境未探索」升级为「环境已探明、阻塞点具体」。
- **备选（否决）**：直接按原文写「设备不可用」——未探测即断言，
  属于拿推测当事实。

### D3：门禁基线只登记实测值，未实测项显式标注

`CI 产物哈希比对` 与 `16KB 页对齐` 两项本轮无法在禁改区内实测（MUST NOT 改
`build.gradle.kts`；`build.yml` 亦不可改）。推测数字入表会让日后实施者误以为
那是量过的。

- **选择**：这两项在 delta 中显式写「本轮未实测」，并给出与基线不同的
  「实施判据」（以产物实际校验为准）。
- **备选（否决）**：留空——留空与「已登记」不可区分，正是本轮要消灭的歧义。

### D4：delta 只 MODIFIED 一条 Requirement，不新增

实测基线属既有台账的自然扩充。拆成新 Requirement 会让
「禁改区四项」这个整体在规范里裂成两块，日后复查须记得两块都读。

- **选择**：MODIFIED `禁改区待维护者裁定项台账（只登记，不实施）`，
  正文保留原有禁令与落地方案表，新增「实测基线」小节与两条 Scenario。
- **备选（否决）**：ADDED 一条「门禁实测基线」——同一件事两个入口，
  与本仓既有台账的组织方式相反。

## Risks / Trade-offs

- **[历史归档变更被再次编辑，观者可能误以为归档内容会流动]** → 每处补勾都写明
  补记时间与依据来源（git 提交号或承接变更节号），使「补记」本身可与「原始记录」
  区分。
- **[模拟器实跑耗时且可能超时]** → 放后台执行并设上限；失败则按 D2 的备选路径
  把探测结果入表，不阻塞其余工作。
- **[工具版本前进使基线失效]** → delta 明写「工具版本可能前进，重跑 MUST 以当日
  实测覆盖本列」，避免基线被当成永久真值。
- **[把 aislop 的 0 error 当作全仓质量结论]** → 已在 delta 的覆盖面限制与
  Scenario「门禁的覆盖面限制被如实记录」中显式禁止。

## Migration Plan

无迁移。改动仅限 `openspec/` 文档；无运行期行为变化，回滚即 `git revert`。

## Open Questions

无。禁改区三项的实施授权属维护者裁定（已裁定为不实施），不构成本变更的设计分歧。
