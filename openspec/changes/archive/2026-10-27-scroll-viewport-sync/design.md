# Design

## Context

滚动位置由两部分组成：整行偏移 `scrollOffset`（行）与亚行余量 `scrollRemainderPx`
（像素）。两者的生效路径完全不在一条线上：

| 分量 | 通路 | 生效时机 |
| --- | --- | --- |
| 整行偏移 | 宿主 → `Command::ScrollViewport` → VT 线程 → `scroll_viewport` | 异步：命令入队后由 VT 处理，处理完才推出新视口帧 |
| 亚行余量 | 宿主 → `setScrollYPx` → 渲染器 `viewport_scroll_px` → `begin_frame` 写 uniform | 立即：下一帧开帧时生效，与视口无关 |

余量的语义是「相对当前视口的行内位移」，故它只在**视口与行偏移对得上**时才有意义。
跨行边界时两者一起变，而生效时刻不同 ⇒ 中间态必然存在。

中间态的视觉代价可算清：边界前余量 0.6h、边界后 0.1h（h 为行高），整行 +1。

- 期望位置：`(T-1)h + 0.6h` → `T·h + 0.1h`，即下移 0.5h（= 手指位移）。
- 实际：旧视口配新余量 → `(T-1)h + 0.1h`（先上跳 0.5h），新视口落地 → `T·h + 0.1h`
  （再下跳 h）。

先上跳半行、再下跳整行，就是「晃动」。

排除过的假设（均有代码依据）：

1. 余量与行高的尺度不一致——两侧都用 `raster_scale == spToPxScale`，口径一致。
2. 空闲路径拿旧视口配新余量——空闲路径有在途门，挡住了。
3. 亚行取整不对称——`scroll-physics-drift` 已钉住截断趋向零，正负阈值对称。
4. 输入法位移振荡——`applyImeShift` 有幂等门，常态 `imeShiftRevealPx = 0`。
5. VT 侧无视口偏移读数——`Terminal::scrollbar()` 是缓存直读，摊还 O(1)。

## Goals / Non-Goals

- Goal：新帧路径与空闲路径口径一致——滚动命令在途期间的陈旧帧一律不呈现。
- Goal：识别陈旧帧不依赖「距离实时视图多少行」这类会漂移的量。
- Goal：宿主侧的余量提交与行偏移提交同拍，杜绝「旧视口配新余量」。
- Non-Goal：不改滚动物理（取整、边界丢弃、惯性曲线）——`scroll-physics-drift`
  已钉住，本变更不碰。
- Non-Goal：不改宿主「行偏移 = 离实时视图多少行」这一模型。它在回滚浏览期间遇到新
  输出会漂移（实测：视口锚在内容上，回滚顶随新输出下移），但那是既有模型问题，
  与本次晃动无关，另行处理。

## Decisions

### 决策一：用请求序号识别陈旧帧，不用视口偏移比对

候选方案是拿帧里的视口绝对行与宿主的目标比。但上游实测否掉了它：

```text
live      = (total=21, offset=16, len=5, scrollback_rows=16)
scrolled  = (total=21, offset=13, len=5, scrollback_rows=16)   ← 上滚 3 行
after out = (total=23, offset=13, len=5, scrollback_rows=18)   ← 回滚中又来 2 行
```

视口**锚在内容上**：回滚浏览期间新输出只把底部推远，锚点不动。于是「离实时视图
多少行」会随输出增长（3 → 5），而宿主的行偏移不变 ⇒ 两者不再可比，拿它判陈旧会
把正常帧误判成陈旧（画面永久冻结）。

请求序号没有这个漂移：它是命令的身份，与内容无关。

- 每次成功送达滚动命令时分配一个序号（进程级单调递增，1 起）。
- VT 处理命令后把序号记在 `RenderExtractors` 上，随下一帧回传（`CursorInfo`）。
- 渲染侧比对帧携带的序号与「宿主已送达的最新序号」：帧的序号更小 ⇒ 该帧早于在途
  命令 ⇒ 陈旧。

序号**不复用**（进程级而非会话级）：会话重启后新请求的序号恒大于重启前的任何
序号，重启前的帧不会被误判成「已反映新命令」。

被否决的替代方案：

- *用视口绝对行*：漂移如上，且「滚动被钳制在边界」时实际行与请求行不等，判定会
  卡死。
- *下发命令前清空帧通道*：清空与命令处理之间仍有并发推帧窗口，清不干净；且丢弃的
  帧内容要靠后续重推补齐，不如序号判定确定。

### 决策二：陈旧帧不呈现，但内容不丢

陈旧帧被丢弃时，VT 侧的滚动命令会**强制重推**一帧（`last_cell_data_push = None`
失效去重基线），那一帧带新视口与新序号 ⇒ 内容与位置都对。故丢弃陈旧帧不会丢内容。

唯一例外是「取帧之后 surface 才被拆走」：此时帧已被破坏性取出，陈旧帧的视口也不会
被后续重推补齐（重推的是滚动后的视口）。该情形按 `render-stability` 的既有约定处理：
帧存入 `last_frame` 并解除滚动在途门控，重挂载后的空闲重绘据此补画。

### 决策三：宿主侧余量随行偏移同拍提交

行偏移未被原生接受时（会话锁被 PTY 写入占用、或命令通道满），原生视口还是旧的。
此时下发余量就是「旧视口配新余量」，与陈旧帧是同一类错配。宿主侧改为：行偏移
未被接受就不提交余量，余量保留旧值、下一帧重试。

代价：洪流期间行偏移本来就推不动，余量也不再走，滚动整体停住而不是抖。这与既有
规范「拿不到即返回未生效，调用方保留上一次已提交的值并在下一帧重试」一致。

### 决策四：陈旧帧诊断记 trace

陈旧帧是逐帧事件（滚动期间每帧都可能命中）。按 `logcat-hygiene`，热路径单次取值
的诊断 MUST 记 trace，MUST NOT 以 debug 逐次输出。

## Risks

- **冻结**：若「已送达的最新序号」推进了而对应的新帧始终不来，所有后续帧都会被判
  陈旧。命令送达后 VT 必定处理并强制重推，故该帧必到；重推因通道满失败时，去重
  基线仍被清空，下一轮继续推。
- **跨会话**：序号是进程级的，请求与帧都属同一会话，跨会话不会误判。切换会话时
  在途门由新会话的帧解除。
- **复位**：终端复位（RIS）不重置序号。复位后的帧携带复位前的序号，与已送达序号
  相比不小 ⇒ 不被判陈旧 ✓。
