# 设计

## 现状与根因

`wait_for_clipboard_answer` 在应答线程上轮询一次性槽位，2s 内没有答复就记一行
`error`；槽位被丢弃（发送端析构）时同样记一行 `error`。

两条都不是真实异常的形态：

- **超时**：宿主暂停渲染时不派发应答。暂停有五个来源（切后台、设置页、Surface
  销毁、交换链与输入法网格两个防抖），期间渲染线程已停，事件留在原生队列等待
  恢复后派发——远端的读请求必然无人应答。宿主仍在渲染时，渲染循环每帧都
  `pollAll`，应答在毫秒级回来，2s 超期说明宿主漏了这条读请求。
- **通道断开**：发送端只由「宿主应答」与「应答线程自己取消」两处释放，前者先发
  后析构、后者发生在等待之后，故这条路径当前不可达。

## 方案

分级依据「宿主此刻是否还在渲染」：仍在渲染却没应答 → warn；已暂停 → debug。
这与 `logcat-hygiene` 的既有判据同构（正常退化记 debug、真异常记 warn），也
与 Kotlin 侧 `transientRenderErrorIsWarning` 的取法一致。

判据的取值不能去读渲染状态：那个锁被整帧 GPU 工作持有，旁路的应答线程去抢它
会与渲染线程互相等待。故在 `setRenderPaused` 导出里同步一份原子镜像，镜像先于
渲染状态落盘（先落的是「宿主的意图」，应答线程据此分级不会晚于渲染状态）。

限频沿用既有的 `slow_log::CountedLogThrottle`：一个窗口一行，行内带窗口内累计
的次数，窗口内的计数延后交出而不丢弃。两种情形各用一把闸门——共用一把会让恢复
渲染后的那次输出把正常退化的次数说成异常。

## 取舍

- 分级从 error 降到 warn/debug：应答缺失的后果是远端读不到剪贴板（请求悬空），
  应用本身没有崩溃、没有丢数据、没有资源泄漏；error 级会让「应用崩了」与「宿主
  暂时没空应答」混为一谈。
- 不用「宿主是否在前台」作判据：前台但设置页打开时同样不派发应答，而后台但
  通知栏在场时前台判定会漂；渲染暂停才是「应答链路是否在跑」的直接事实。
- 通道断开与超时共用一条诊断出口：两者的含义相同（宿主没给出答复），分开写
  两套分级只会让口径分叉。

## 验证

- 单测：宿主暂停 → debug、宿主仍在渲染 → warn；首条缺失立即交出窗口计数，
  窗口内的缺失攒着下次交出；渲染暂停镜像跟随宿主的暂停与恢复。
- `cargo test --lib`、`cargo clippy --all-targets -- -D warnings`、`cargo fmt --check`。
