# Design

## 问题定位

`NotificationManager.notify(id, notification)` 的 id 在整个应用内唯一：同 id 是同一条通
知，后发的顶替先发的。当前两处通知都落在同一张表里：

| 通知 | id | 渠道 |
| --- | --- | --- |
| 前台服务常驻通知 | 固定 1 | `terminal` |
| 桌面通知（OSC 9 / OSC 777） | `sessionId.toInt()` | `desktop_notification` |

会话 id 由原生侧单调自增（`NEXT_SESSION_ID` 从 1 起），首个会话即 id 1，与常驻通知
的 id 相同。两处顶替都真实可发生：

- 后台收到首个会话的 OSC 9 提醒 → `notify(1, 桌面通知)` → 常驻通知被顶掉，通知栏里
  不再有「退出」与「唤醒锁」入口；
- 随后会话数变化 → `startForeground(1, 常驻通知)` → 刚收到的提醒被顶掉。

渠道不同并不能隔离二者：id 冲突发生在通知表里，与渠道无关。

## 方案选择

**桌面通知的 id 落在独立号段，由会话 id 派生。**

- 换掉前台服务的 id 不解决问题：会话 id 覆盖整个正整数空间，任何固定 id 迟早与某个
  会话 id 相撞；常驻通知只有一个，把冲突推给桌面通知才是把问题挪个位置；
- 用独立的自增计数器给桌面通知发号，则同一会话的后续通知会在通知栏里堆叠，不再顶
  替先前那条——这是行为变化，而「同一会话只留最新一条」是既有行为，不该顺带改掉；
- 号段法保留「同一会话恒得同一 id」的语义，同时把桌面通知的 id 挪出常驻通知所在的
  取值。

**号段自 1_000_000 起、容量 1_000_000。**

- 取模使结果恒落在 `[1_000_000, 2_000_000)`，既不会与常驻通知的 id 1 相撞，也不会
  溢出成负数；
- 会话 id 由原生侧单调自增，一个进程内的实际取值远小于号段容量；号段容量取 100 万
  是为了让「两个存活会话撞到同一 id」所需的会话数远超任何真实进程能造出的规模。

**PendingIntent 请求码用同一个 id。**

`PendingIntent` 的同一性由「请求码 + Intent 过滤比较」决定。前台服务的请求码是 0..3
（打开、退出、唤醒锁），桌面通知的请求码取桌面通知 id 后与它们彻底分开。同一会话的
多次通知请求码相同，配合 `FLAG_UPDATE_CURRENT` 仍复用同一条 `PendingIntent`——既有
行为不变。

## 验证方式

- 纯函数单测：同一会话恒得同一 id；桌面通知的 id 不等于常驻通知的 id 1。
- Robolectric 行为单测：常驻通知在场时投递桌面通知，通知栏里两条并存；常驻通知刷新
  后，桌面通知仍在。
