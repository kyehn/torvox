# 设计

## 现状与根因

宿主渲染循环里有四条失败诊断路径，它们的输出决策全都挂在「连续错误数」上：

| 路径 | 旧的输出条件 |
| --- | --- |
| 瞬时渲染错误（`render()` 返回负数） | `consecutive == 0` 或每 50 次连续错误记一行 |
| 渲染异常（`render()` 抛异常） | `consecutive == 1`（首条）或每 60 次记一行 |
| 错误后恢复 | 每次成功且此前有错即记一行 |
| 输出泵失败（`pollAll()` 抛异常） | 无节流，每次都记一行 |

关键事实：**成功一帧就把连续错误数清零**。于是「失败—成功—失败」的交替形态下连
续数每次都是 0 或 1，四个条件每次都命中，每帧记一行。渲染异常那条还带完整栈，一
帧一行栈把 logcat 刷满，真正的缺陷反而被淹没。

输出泵失败此前根本不限频：桥接层持续抛异常时每帧一条 error 加栈。

## 方案

### 账本：连续数与输出决策分开

新增 `RenderErrorLedger`（纯 Kotlin，可在 JVM 上单测），持有：

- 连续错误数：只服务退避档位（`renderErrorBackoffMillis`）与致命上限
  （`RENDER_MAX_CONSECUTIVE_ERRORS`）。
- 四把窗口闸门：瞬时错误、渲染异常、错误后恢复、输出泵失败各持一把。四类诊断互
  不共用——共用会让先到的那类吞掉后到的次数，规范明令禁止（「慢循环与慢帧各自限频」）。

闸门沿用既有的 `CountedLogThrottle`（500ms 窗口，放行时交出窗口内累计次数），与原
生侧同一套机制。

### 分级口径改为含本次在内

瞬时渲染错误的分级判据是「首次是正常退化（平台收走了原生窗口），连续出现才是异
常」。账本在记这一次错误时就已累加连续数，故分级改按含本次在内的计数：1 = 首次
（info），≥2 = 连续出现（warn）。判据本身没变，只是计数基准从「本次之前」挪到
「含本次」。

### 栈只给孤立的一次

成堆重复时同一异常的栈并不变，每 500ms 重复一份只会把 logcat 刷满。故完整栈只
在窗口内仅此一次时给出；成堆时行内给出异常类型与窗口内次数，信息不丢。

### 标题查询的 catch 是死代码

`NativeQueryPort.getTitle()` 在原生侧没有标题数据时返回 null，查询端口归为缺省值
（空串），不抛异常；取消信号由 `onQuery` 原样上抛。渲染循环里那段 catch 因此永不
可达，且它把取消信号也当成失败——应用收尾时留下一条假 error。直接去掉。

## 取舍

- 不改退避档位与致命上限：它们的语义（连续错误）没有错，只是不能兼作输出决策。
- 不改失败诊断的等级：瞬时错误首次仍是 info、连续出现仍是 warn；渲染异常与输出
  泵失败仍是 error。
- 窗口取 500ms（规范下限，与原生侧同档）。窗口内攒下的次数延后交出而非丢弃。
