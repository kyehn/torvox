# 设计

## 现状与根因

规范对逐帧诊断的要求有两层：按窗口输出（每窗口至多一行），以及行内带上窗口内的
事件计数。本变更涉及的三处都只满足前一半，且都处在逐帧路径上。

### 滚动指令投递失败

`setScrollOffset` 在滚动期间每帧被调用一次。命令通道满时投递失败，旧的实现每帧
记一行 warn。滚动是用户手势驱动的连续动作，通道满时往往持续数十帧，于是告警成
片刷出。

### 渲染遇到未知会话

`collect_frame_data` 每帧查一次会话注册表。查不到时旧实现每帧记一行 warn。会话
被销毁后宿主若仍在渲染它（销毁与渲染循环停止之间存在窗口），告警会逐帧刷出。

### VT 应答写回失败

失败的应答退回队首、下帧重试：子进程不读 stdin 时每帧都失败，每帧记一条 error。
更糟的是子进程已退出时旧实现同样逐帧重试——读端已消失，应答永远无人接收，
「子进程已退出」这一正常退化被记成 error 洪水。

## 方案

三处各改用 `slow_log::CountedLogThrottle`：记一次事件，闸门放行时交出窗口内累计
的事件数，窗口内则继续攒着。三者是不同的事，各持一把闸门——共用会让先到的诊断
吞掉后到的次数。

字段命名：滚动投递失败用 `failed_scrolls`，未知会话渲染用
`unknown_session_frames`（计的是命中的帧数，不是会话数），VT 应答写回失败用
`failed_writes`。

VT 应答写回另加退出态短路：`drain_pty_write_back` 先判 `is_exited()`，是则丢弃
待写应答并记 debug。VT 引擎侧的应答缓冲也要一并抽干——上游回调逐条 push，不抽
则它无界增长。

## 取舍

- 写回失败仍是 error：子进程活着却不读 stdin 是真实异常，不是正常退化。只有
  「子进程已退出」这一条降为 debug。
- 不改失败后的续写语义：未写出的部分仍退回队首下帧续写，只退回未写出的部分
  （避免子应用收到重复应答）。
- 未知会话仍是 warn：宿主在会话销毁后仍渲染它是真实的时序异常，只是洪泛的
  形状由窗口计数给出。

## 验证

- 回归用例：子进程已退出时待写应答被丢弃且不写 PTY；写回失败按窗口汇总，失败
  的应答仍留在队首。
- `cargo test --lib`、`cargo clippy --all-targets -- -D warnings`、`cargo fmt --check`。
