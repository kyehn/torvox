# 设计：审计遗留项台账的分类口径与核实要求

## 1. 为什么是台账而不是 spec

本变更不改变任何可观测行为：它把 `docs/REVIEW*.md` 中**尚未解决**的条目按
「真实缺陷 / 需裁决 / 需授权 / 已否证」四类落账，随后删除原始审计文档。

因此 `.openspec.yaml` 声明 `skip_specs`——若为这些条目编造行为契约，等于把
「还没做到的事」写成「规范要求做到的事」，反而制造新的文档债。

## 2. 四类口径

| 类别 | 定义 | 处置 |
| --- | --- | --- |
| 真实缺陷 | 代码行为违反 `docs/specification/` 明文条款，或可构造用户可观察的错误状态 | 进 tasks，按严重度排序，逐条独立提交 |
| 需裁决 | 规范之间或规范与实现的**字面**冲突，修哪边是产品决定 | 进 tasks，标注需用户回答的问题 |
| 需授权 | 修复必然改动保护文件（`.github/`、`scripts/`、`flake.nix`、`*.gradle.kts`、`detekt.yml`、`lint.xml`、`.semgrep/*`、`docs/specification/`） | 进 tasks，标注授权点，不擅自改动 |
| 已否证 | 审计时成立、本轮回读源码后确认已不成立 | 记录否证依据，防止重复排查 |

## 3. 核实要求（本轮已执行）

审计文档写于数周之前，其间已有大量修复。仅凭文档判断「仍成立」会把已修项
误记为未修，稀释台账价值。故每条至少满足其一才入「真实缺陷」：

1. 给出当前 `文件:行` 的回读证据；或
2. 给出构造该错误状态的用户可见路径。

无法回读证实的条目归入「需复核」，不得直接列为缺陷。

**已否证的典型**（记录依据，避免重复劳动）：

- 目录被标 `FLAG_SUPPORTS_DELETE` —— 审计称 SAF 对文件夹显示删除后抛
  `FileNotFoundException`；回读 `DocumentMutations.deleteWithoutFollowingSymlinks`
  见目录已先序收集、逆序删除，目录删除**确实实现**。声明与实现一致，不改。
- `RenderWatchDog.stop()` 阻塞化 —— 现为非阻塞（`job.cancel()` + `fireLock`）。
- 选区行钳位用错坐标系 —— 已改绝对空间（`cachedScrollbackLength` 同源）。
- `row_cache` / `cached_scrollback` 只写字段 —— 全仓已无该字段。

## 4. 删除原始文档的前置条件

删除 `docs/REVIEW*.md` 之前，本台账必须已包含：

1. 全部仍成立的真实缺陷（含文件:行与用户可见后果）；
2. 全部需裁决项（含具体问题，而非「请决定」）；
3. 全部需授权项（含要改哪个保护文件的哪一处）；
4. 已否证项及其依据。

否则删除等于隐藏未完成的工作。
