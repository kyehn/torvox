# 设计

## 现状与根因

规范对限频诊断的要求有两层：按窗口输出（每窗口至多一行），以及行内带上窗口内的
事件计数。OSC 52 读请求路径上的两条告警只满足前一半。

### 读请求洪泛削减

远端持续发 OSC 52 读请求时，未作答计数超限即就地显式作答空串（洪泛削减）。削减
按请求逐条发生，每帧至多 `MAX_FLOOD_SHED_ANSWERS_PER_FRAME` 条，故这条告警在
洪泛持续时逐请求命中。旧实现每 5s 至多记一行，行内只有当刻的未作答积压量
（`unanswered`），没有窗口内削减了多少条。

### 选择器名超长

选择器名超过 `MAX_SCAN_BYTES` 时该读请求透传而不作答，并记一条 warn。程序可反复
发超长选择器，故这条告警同样逐请求命中；旧实现每 5s 至多记一行，次数不可见。

两条都是不同的事（削减、超长），各持一把闸门——共用会让先到的诊断吞掉后到的
次数。

## 方案

两处都改用 `slow_log::CountedLogThrottle`：记一次事件，闸门放行时交出窗口内累计
的事件数，窗口内则继续攒着。两处的静默期都是 5s，与既有的洪泛告警同档，故用
`CountedLogThrottle::with_interval` 配置，不另写私有闸门。

字段命名：削减用 `shed_reads`（计的是被削减的读请求条数），超长用
`oversized_selections`。

洪泛削减行保留 `unanswered`：它是当刻的积压量，是升级信号；窗口内累计条数补的是
另一个维度——一段时间里削减了多少。

## 取舍

- 不改分级：两条仍是 warn。洪泛削减意味着远端行为异常，超长选择器意味着请求无法
  被应答，都不是正常退化。
- 不改削减与截断策略本身。

## 验证

- `cargo test --lib`、`cargo clippy --all-targets -- -D warnings`、`cargo fmt --check`。
