# 设计

## 现状

规模约束、超大文件治理、参考留档齐备性与门禁一致性这四条，目前都靠「读代码觉得还行」
判断，没有可复算的坐标：

1. 规模约束写在样式规范里，但没有说明按什么计数、生产与测试是否分列、对照基线取哪一
   档数字，也没有任何步骤去度量。审查时用同一份代码、两种口径得到相反结论。
2. 原生侧曾按约 1100 行的固定阈值拆分，设计文档明确「拆分依据是职责，不是行数」；
   同一阈值没有应用到界面与运行时侧，五千行级文件仍在。
3. 设计文档明列三个参考项目，参考资料目录只有两份对应留档，第三个恰是同类度最高的
   Kotlin 与 Compose 实现。
4. 测试规范声明两项静态检查工具，验证脚本与持续集成实际执行的是格式、静态分析、单元
   测试、界面测试与规范校验，没有那两项。历史拆分曾引用其中一项的告警，说明工具可用。

规范自我要求「靠固定参数扫描判定、留下可复算的留档」，唯独这四条缺扫描参数与留档位置。

## 口径设计

### 规模口径

计数单位固定为源码行数：排除空行、纯注释行、块注释、文档、配置、资源、构建产物与第三方
代码；生产与测试按路径判定并分列；参考项目用同一脚本、同一参数重跑。用户已明确代码量
不是存储占用，故不以磁盘字节或仓库体积排序。

对照基线取两个点名参考项目的生产源码行数之和；判定必须同时报出生产、测试与源码合计
三档，并写明所用口径。审查留档保存本次实测数字作为基线，后续复算与基线比对，偏差须
给出解释。规模问题不得通过删除测试解决，测试规范要求高覆盖且每个测试断言具体结果。

### 跨语言阈值

同一阈值 MUST 同时应用于所有源码语言，不允许只对原生侧生效。拆分依据是彼此独立的职责
边界，不是按行数机械切分：样式规范反对一次性抽象、要求仅用一次的辅助类型优先内联，
因此方案是重组关注面而非制造空壳类型。保留超限文件须逐条写明理由并留档。

### 参考留档齐备性

清点设计文档明列的参考项目，逐个核对参考资料目录是否有对应留档；缺失记为资料齐备性
缺口并写明补齐内容范围。补齐落点是受保护目录，须在获得明确同意后进行；未获同意时登记
为待办，不得以改文档之外的手段绕过。

### 门禁一致性

逐条列出验证脚本与持续集成实际执行的命令，与测试规范的声明比对；不一致登记为未完成，
写明差异位置与接入方式由谁决定。声称某项检查通过时，证据须指向实际执行的命令，不得
以规范声明代替执行记录。

## 不作处置的边界

| 候选 | 不作处置的理由 |
| --- | --- |
| 换 VT 引擎或渲染栈 | 设计文档已指定实现，换核违反架构单一来源 |
| 用绑定生成框架替换手写 JNI | 设计文档规定直接调用，且属改源码 |
| 帧时间线关联与真实 PTY 捕获重放 | 既有的研究收口文档已评估并否决 |
| 用视觉基线替换现有界面测试 | 测试规范指定既有断言体系，且属改测试 |
| 删测试降规模 | 测试规范要求高覆盖，规模问题由口径与门禁解决 |
| 直接改验证脚本或工作流加门禁 | 二者是受保护文件，且样式规范禁止提交生成的配置或脚本 |
| 直接拆分大文件 | 属改源码，本次只产出方案与规约 |

## 验证

- 规约增量经 `openspec validate --all --strict` 校验，既有能力保持全绿。
- 逐文件覆盖清单、反模式命中明细与逐条判定结果按轮次留档，可与审查报告表格逐项核对。
- 受保护文件改动前后摘要逐一比对，确认零误改。
- 统一口径的统计脚本对本项目与参考项目用同一参数重跑，数字与留档表格一致。
- 本地树与远端主分支树逐文件比对，含可执行位。
