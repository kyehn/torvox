# Design

## 现状证据

### 帧节拍与空闲闭锁

`TerminalRuntime` 中注册唯一的自调度 `Choreographer.FrameCallback`，每次回调
只把激活会话的空闲时钟、滚动运动状态、`vsyncRequested` 与一次原生唤醒
合并到下一次呈现，不在主线程绘制。链到达后 `doFrame` 无条件重新投递。
活性闭锁分三档：

| 当前值 | 行为 |
| --- | --- |
| 17ms 兜底 | vsync 链停摆时仍可跟进输入回显 |
| 34ms 安全网 | vsync 健康时避免与 17ms 定时器同周期重复推帧 |
| 100ms 新鲜度 | 超过后主线程被视为被阻塞，退回 17ms 兜底 |
| 500ms 空闲闭锁 | 距上次信号 5 秒且无滚动运动时避免空闲轮询 |
| 250ms 运动窗口 | 手势停止后回到空闲策略 |

当主线程被输入法或组合评分占据时，`Choreographer` 可能静默丢弃已经排队
的帧回调；实现并不依赖每次回调都及时返回，因为停摆兜底会接管。

### 弱点

1. 60Hz 假设的固定换算写在注释中，但健康安全网的语义已经是
   “至少大于一个显示周期”，不是帧预算。若设备运行在 120Hz，17ms
   兜底约两个周期，34ms 约四个周期，XML 已经过大，但仍保持每周期
   至多一帧；不能据此推断“每帧固定等于 16.7ms”。
2. 链健康性只看时间戳，适合作为切换安全网的信号，但没有记录实际
   vsync 周期。仅在结果里写 `17ms` 会误以为固定帧率。
3. 当前仍使用无条件重投，即使长时间空闲也会每帧唤醒主线程。
   链被保存下来的错误注释理由（闪相位）已不存在；`render-loop-scroll-cadence`
   要求合并，`render-stability` 要求 dirty/forceRender 双通道，现有空闲策略
   不依赖链常驻，因此停止链是合理设计。

### 参考项目

| 项目 | 帧驱动与唤醒策略 |
| --- | --- |
| 本项目 | Choreographer 每帧门控 + 定时闭锁安全网；5 秒空闲后停泵，500ms 闭锁 |
| termux-app | 输出后按需重绘，没有固定逐帧回调 |
| ghostty-android-terminal | 输出/事件驱动的原生绘制，本层没有逐帧 Choreographer |
| termlib | 快照在后台 dispatcher 合并，Compose 在 frame clock 上应用快照 |
| Drosh | `Choreographer.FrameCallback` 轮询 `poll`/`onWakeup`，GLSurface WHEN_DIRTY；有 `start()`/`stop()` 与 blink 管理，链本身仍是每 vsync 活跃 |
| awkox/AndroidTerminal | Compose 直接消费状态流，没有自调度逐帧回调 |

补充结论：本项目仅靠“输出唤醒”并不足以在省电状态下始终按
当前显示周期工作。显示帧回调是节拍的唯一真实来源，定时仅作安全网。

### 平台口径

- Android 官方文档要求应用不要假设刷新率不变；若关心刷新率，应读取
  当前显示模式，并在刷新率变化时重新读取。
- 系统可能因省电模式或热节流把显示刷新率限到 60Hz；活动工作必须仍正确。
- 固定帧率声明是偏好，不是硬件事实；固定为 120 而当前显示最多 90 时
  实际只有 90，而且空闲时继续要求高帧率会反向耗电。
- 活跃闭锁超时不得成为与显示帧相同的第二路节拍；不能把固定毫秒
  常量改造成“等待时间等于帧时间预算”。

## 设计决定

### 显示节拍优先：唯一帧源

显示帧回调是帧节拍的唯一真实来源。定时闭锁只负责唤醒等待者唤醒在
链路层失事时的兜底；它不拥有帧的提交。

### 电源状态不侵入渲染

- 不读取 `PowerManager.isPowerSaveMode` 来选择渲染路径。
  平台的刷新率上限已经自动限制帧率，空闲策略也不需要省电模式开关。
  读取它会让显示上限、免打扰环境等无关状态改变渲染正确性。
- 不在空闲期用 `setFrameRate` 强制 60Hz 或强制 120Hz。
  恰好空闲时显示刷新率本来可以更低，强制只能提高功耗。
- 闭锁常量统一按“显示周期倍数”描述。17ms 和 34ms 是当前对
  60Hz 周期（约 16.7ms）的近似换算，不是框架帧预算。不能把
  “更快必须缩短安全网”当作规范。

### vSync 链必须有启停

停链条件任一满足即逐帧停：没有会话、宿主不可见、连续空闲超过阈值且
可观察到的活跃动画没有持有“帧租约”。重启条件：会话启动、切换会话、
PTY 输出到达、输入写入、搜索/选区变更、恢复前台。

### 刷新率可观察性

帧时长窗口应使用 `doFrame` 提供的实际 vsync 时间戳差值，
而不是把 `frameTimeNanos` 与进程内最后一次输出时间差混合使用。
展示分档应以窗口内实际 vsync 间隔计算（平均值、中位数、p95），
而不以固定分母 16.7ms 计算 FPS。当前代码没有接入此数据源，
所以列为未完成。

### 前台服务的执行锁定位

- 执行锁的唯一目的是让 shell 子进程在后台/亮屏、灭屏时仍能得到
  CPU。验证方式：`TerminalForegroundService` 只有一个 `PartialWakeLock`，
  持有时长和续期必须可由会话计数推断。
- `wakeLock` 不在空闲会话里全程持有；获取路径必须在会话数升至 1 时运行。
- `wakeLock` 超时是安全网。在持有锁期间续期，锁在获取路径被重取；
  可能不满足“暂停后继续持有”的前置时，为了继续任务，必须重新获取。
- Wi-Fi 锁只在有会话的进程生命周期内持有。平台最终只允许高性能模式
  按低延迟锁对待，不会让它变成比低延迟锁更差的策略；灭屏时必须
  保持可用，不可依赖临时省电状态自动降级。
- `preHandleTaskRemoved` 不是一般执行锁管理：任务被划去且终端会话
  仍有会话时，重新获取唤醒锁和 Wi-Fi 锁；零会话则不获取。

## 不作处置的边界

- 不修改源码、测试、Manifest、脚本或受保护文件。
- 不读取省电模式选择渲染路径、字体、色彩、节拍等。
- 不建议固定高刷新率的声明、后台 `PowerManager` 分支、为高刷单独写
  的第二套节拍、单独的截图基线计时器。
- 不用显示器读取值来代替应用需要的帧预算；真正帧预算是当前设备
  实际 vsync 周期。
- 不修改状态文档；若要将残余问题收口，需要用户明确授权。

## 验收方式

- OpenSpec 规约增量通过 `openspec validate --all --strict`。
- 与现有 capabilities（`render-loop-scroll-cadence`、`display-adaptation`、
  `terminal-foreground-service`、`code-health`）无矛盾。
- 文档指出仪器化数据源未完成，不误导为“已存在”。
- 对图标设备做 60/120Hz 与真实省电模式复测：输入回显、滚动合并、
  空闲闭锁与后台输出均无黑屏、无丢帧放大。
