# Design

## 决策

### 决策一：每轮排空上限取 32，与事件队列同口径

事件队列的每帧上限是 `MAX_EVENTS_PER_POLL`（32），通知排空取同值：两者面对的都是
「远端程序可无限触发」的输入，量级相同；上限不同会让两条路径在同一台设备上表现不一致。

实现上直接引用同一个常量（通知侧为 `MAX_NOTIFICATIONS_PER_DRAIN = Bridge.MAX_EVENTS_PER_POLL`），
不让两处各写一个 32 而日后漂移。

上限不是丢弃阈值：达到上限只是结束本轮，剩余通知留在原生队列里，下一轮继续排空。
原生队列自身有界（满时丢最旧并告警），故内存不随洪泛增长。

### 决策二：轮询入口先取后推进

轮询入口改为「先取已入队的通知；取不到才推进会话收割」。理由：

- 通知的产出本就靠会话推进（VT 解析 OSC 9 才触发上游回调），而推进在生产路径上由
  渲染循环与后台推进泵承担；轮询入口自带推进只是兜底（冒烟测试没有渲染循环）。
- 兜底不必每条通知做一次。排空循环每取一条通知就调一次入口，先推进后取即等于每条
  通知一次全量推进：洪泛时那会把一次收割放大成上百次会话推进，与渲染线程争会话锁。

「取不到才推进」不影响正确性：队列非空说明已有通知待取，此时推进与否都不改变这一轮
的取用结果；队列为空才可能存在「各会话已产出、尚未收割」的待上报通知，此时推进一次
即可收割。

### 决策三：宿主侧不再另设通知缓冲

超出上限的通知留在原生队列，不在宿主侧另设缓冲或批量数组接口。理由：原生队列已经有
界与淘汰语义，宿主再缓冲一份就要重写一遍淘汰规则，并引入「两份队列各淘汰一次」的
顺序歧义；批量返回则要改 JSON 形状（`pollNotificationEvent` 的形状已登记在
`upstream-alignment` 的「保留 JSON 的边界登记」里）。

## 风险

- 通知洪泛时投递速率被上限压住（每轮最多 32 条，轮询间隔 100ms）：这是有意的背压，
  通知本身是提示而非状态，迟到的通知仍会依次送达。
- 排空上限之外的通知依赖下一轮继续排空：轮询协程每轮都会回到等待点，故不会饿死。
