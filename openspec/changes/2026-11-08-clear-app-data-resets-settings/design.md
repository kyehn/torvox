# Design

## 现状

- `TerminalViewModel.clearAppData()`：停掉引导 URL 的防抖写入 → 删除 `prefs` 目录与
  缓存目录项 → 重建 `prefs` 目录 → 提示「已清除」。
- 设置存储是 Hilt 单例（`SettingsDataStoreProvider` → `DataStore`），进程内长期存活。
- `DataStoreImpl` 读路径先看内存缓存：命中即为终态则直接返回，不回磁盘；写入在内存
  状态上合并后整份落盘。

由此得到两个后果：

1. 删掉 `preferences_pb` 之后，存储仍按缓存里的旧值供给，界面显示清除前的设置。
2. 清除后的第一次写入把缓存里的整份旧状态连同新值写回文件，已删的设置逐个复活。

## 设计决定

### 先经存储清空，再删目录

清空动作交给存储自身（`edit { clear() }`）：它在同一次写事务里把内存态清空并落盘，
两个状态同时归零。随后删目录只是把物理文件清掉，内存态已经是空的，两者不冲突。

不选「只删目录」：那是当前行为，内存态留着旧值。
不选「删目录后重建 DataStore 实例」：仓库的各条流在构造期就绑定了具体实例，换实例
要把它们改成动态取值；而且重建实例与旧实例短暂并存时，同一文件上会同时存在两个
活动实例，DataStore 直接抛错。
不选「只清内存不删文件」：目录里可能残留临时文件与备份文件，「清除」应把它们一并
清掉。

### 与既有清除动作的关系

引导 URL 的防抖写入仍由「清除轮次」作废：清空设置内容与停用写入是两道不同的闸门，
前者管已落盘的值，后者管尚未到期的待写值。

## 验证

- 单测：设置过字号、Shell 入口与字体族后清除，三项都回落缺省。
- 单测：清除后删掉 prefs 目录并重建，设置读到的仍是空值。
- 单测：清除后再写一个值，落盘文件里只有新值，清除前的标记值不在其中。
