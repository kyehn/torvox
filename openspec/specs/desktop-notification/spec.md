# desktop-notification Specification

## Purpose

终端程序用 OSC 9 / OSC 777 请求桌面通知（长任务完成、提醒类输出）。本能力规定这些
通知的采集、分派与点击回跳：通知按会话归属送达宿主，应用在前台以应用内提示通道呈现、
位于后台以系统通知呈现，点击系统通知切回通知所属的会话。

## Requirements

### Requirement: 终端通知必须按会话采集并投递

终端程序发出的桌面通知（OSC 9 与 OSC 777）MUST 被采集，并按会话归属投递给宿主：
投递内容 MUST 含会话归属、通知标题与通知正文。

通知负载是程序给出的原始字节，MUST NOT 因非 UTF-8 字节导致失败；解码 MUST 采用替换
字符口径，不得静默丢弃整条通知。

通知 MUST 有界：队列溢出时 MUST 丢弃最旧的一条并记录告警，MUST NOT 让内存随程序发送
速率增长。

#### Scenario: OSC 9 通知被投递

- **WHEN** 终端程序发出 OSC 9 通知
- **THEN** 宿主收到该会话的一条通知，正文为通知内容

#### Scenario: OSC 777 通知带标题

- **WHEN** 终端程序发出 OSC 777 通知
- **THEN** 宿主收到该会话的一条通知，标题与正文均与程序给出的一致

#### Scenario: 非 UTF-8 负载不导致失败

- **WHEN** 通知负载含非法 UTF-8 字节
- **THEN** 通知仍被投递，非法字节按替换字符解码，宿主不崩溃

#### Scenario: 通知洪泛时队列有界

- **WHEN** 终端程序以快于宿主消费的速度连续发出通知
- **THEN** 待投递通知的数量保持有界，最旧的被丢弃且有告警记录

### Requirement: 通知的分派形态由应用前后台状态与呈现通道决定

通知的呈现形态 MUST 由应用是否位于前台决定：位于前台时 MUST 以应用内提示通道呈现，
位于后台时 MUST 以系统通知呈现。两种形态的内容 MUST 含会话序号与通知正文。

前后台的判据 MUST 是应用自身的前后台状态，MUST NOT 用「渲染是否暂停」代替——设置页等
仅暂停渲染的情形下应用仍在前台。

前台呈现 MUST NOT 借用平台提示窗口：该窗口受同一 UID 窗口独占、窗口生命周期与按包频率
限额三条约束，三条都会由平台打出 W 级条目，且超额时提示被直接丢弃。

系统通知在投递前 MUST 确认通知开关处于开启状态：通知被用户关闭时宿主无法发出通知，
此时 MUST 留下诊断而非让通知凭空消失；诊断 MUST 按窗口汇总，MUST NOT 逐条刷屏。

#### Scenario: 前台以应用内提示呈现

- **WHEN** 应用位于前台且收到通知
- **THEN** 通知以应用内提示通道呈现，内容含会话序号与通知正文

#### Scenario: 后台以系统通知呈现

- **WHEN** 应用位于后台且收到通知
- **THEN** 通知以系统通知呈现，内容含会话序号与通知正文

#### Scenario: 渲染暂停但应用在前台

- **WHEN** 应用位于前台但渲染处于暂停状态且收到通知
- **THEN** 通知仍以应用内提示通道呈现，不以系统通知呈现

#### Scenario: 通知被用户关闭

- **WHEN** 应用位于后台收到通知，但用户已关闭本应用的通知
- **THEN** 该条通知不投递到系统通知栏，且宿主留下诊断说明通知被丢弃及丢弃条数

#### Scenario: 前台通知不得产生平台提示窗口条目

- **WHEN** 应用位于前台且连续收到多条通知
- **THEN** 平台 MUST NOT 报出提示窗口冲突、提示令牌生命周期或提示配额告警
### Requirement: 通知投递不得依赖渲染生命周期

应用位于后台期间产生的通知 MUST 在后台期间投递，MUST NOT 滞留到用户回到应用才呈现；
投递 MUST NOT 以「渲染线程正在运行」为前提。

#### Scenario: 后台期间的通知不被滞留

- **WHEN** 应用位于后台期间收到通知
- **THEN** 通知在应用回到前台之前即已按后台形态投递

### Requirement: 系统通知的点击必须切换到目标会话

系统通知 MUST 带会话归属；用户点击后，应用 MUST 切换到该通知所属的会话。切换所需的
表面在点击时尚未就绪时，MUST 等待其就绪后完成切换，MUST NOT 静默丢弃切换请求。

Activity 重建时重复投递的同一个启动 Intent MUST NOT 再次切换会话——用户在重建前
手动切走的会话不得被拽回去。

#### Scenario: 点击通知切换会话

- **WHEN** 用户点击某会话发出的系统通知
- **THEN** 应用切换到该会话

#### Scenario: 表面未就绪时等待后切换

- **WHEN** 用户点击系统通知时渲染表面尚未就绪
- **THEN** 待表面就绪后应用完成切换，不丢失该请求

#### Scenario: 重建不重放通知切换

- **WHEN** Activity 因配置变更重建并再次收到带会话 id 的启动 Intent
- **THEN** 不再次切换会话，用户当前所在会话保持不变

### Requirement: 通知排空必须有界

宿主每轮排空待投递通知的条数 MUST 有上限。达到上限后 MUST 结束本轮并回到等待点，MUST
NOT 因通知持续产生而无限排空；超出上限的通知 MUST 留在原生队列中，由下一轮继续排空，
MUST NOT 因分轮而丢失。

#### Scenario: 通知洪泛时排空有界

- **WHEN** 终端程序持续发出通知，产出速率不低于宿主的消费速率
- **THEN** 每轮排空的通知条数不超过上限，轮询回到等待点，其余通知留在原生队列中

#### Scenario: 超出上限的通知在下一轮继续排空

- **WHEN** 一轮排空达到上限后仍有通知留在队列中
- **THEN** 下一轮继续排空这些通知

### Requirement: 轮询入口只在无通知可取时推进会话

通知轮询入口 MUST 先取已入队的通知；仅当取不到通知时 MUST 推进会话以收割各会话的待
上报通知。MUST NOT 为每条取出的通知推进一次会话。

#### Scenario: 取到通知时不推进会话

- **WHEN** 轮询入口取到一条已入队的通知
- **THEN** 该次取用不推进会话

#### Scenario: 取不到通知时推进会话并收割

- **WHEN** 轮询入口取不到通知
- **THEN** 轮询入口推进会话一次，随后取用收割到的通知

### Requirement: 系统通知的标识必须与常驻通知分开

系统通知的 id MUST NOT 与前台服务的常驻通知相同：同 id 即同一条通知，桌面通知会顶掉
常驻通知，常驻通知刷新也会顶掉桌面通知。

桌面通知的 id MUST 由会话 id 派生；同一会话 MUST 得到同一 id，使该会话的后续通知
顶替先前那条，不同会话 MUST 得到不同 id。

#### Scenario: 桌面通知与常驻通知并存

- **WHEN** 应用在后台收到首个会话的桌面通知
- **THEN** 通知栏里同时存在常驻通知与该桌面通知

#### Scenario: 常驻通知刷新不影响桌面通知

- **WHEN** 会话数变化导致常驻通知刷新
- **THEN** 已投递的桌面通知仍在通知栏里
