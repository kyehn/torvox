# vt-query-latency Specification

## Purpose

VT 线程是终端状态的唯一归属方：渲染线程、UI 线程与事件收割都通过**查询**读它。
查询的应答延迟直接落在渲染帧上——渲染线程的 kitty 放置查询走的就是这条路，
一次查询多等 50ms 就等于丢掉一帧。本能力规定查询的应答延迟不得被 VT 线程的
空闲节拍串行化。

## Requirements

### Requirement: 查询到达即应答，不得等空闲节拍

VT 线程 MUST 同时等待命令通道与查询通道：任一通道就绪即唤醒并处理。
查询 MUST 在到达后立即应答，MUST NOT 等到空闲节拍（`VT_IDLE_TICK_MS`）到点才被排空。
空闲节拍 MUST 只承担周期职责——排空通道里**残留**的查询，以及在状态变化后推送单元数据。

实现：VT 线程的命令循环用 `flume::Selector` 同时监听命令通道与查询通道；
查询就绪时取出该查询，连同通道里其余查询一并应答。命令与查询同属一条逻辑队列：
应答查询前先取走已入队的命令，查询因而能看到命令的效果。

#### Scenario: 空闲终端的连续查询不被节拍串行化

- **WHEN** 终端空闲（无命令在途）时连续发起 8 次查询
- **THEN** 8 次查询的总耗时 MUST 小于两个空闲节拍（100ms）；
    被节拍串行化的实现每轮都等满一个节拍（实测约 384ms）

#### Scenario: 命令与查询同时到达时都被处理

- **WHEN** 命令通道与查询通道同时有消息
- **THEN** 两者 MUST 都被处理：命令进命令批处理，查询立即应答，
    两者都不得因等待另一条通道而延后

#### Scenario: 查询通道断开后继续按命令工作

- **WHEN** 查询通道断开（会话销毁）
- **THEN** VT 线程 MUST NOT 继续在已断开的通道上等待（那会变成忙等），
    MUST 继续按命令通道工作直至命令通道也断开

### Requirement: 命令批必须有时长与条数上界

VT 线程的命令批 MUST 同时受条数上界与时长上界约束。批尾是**唯一**的查询应答点，
批若无界（只等命令通道排空），持续输出下通道恒非空：批永远不结束，查询无人应答，
逐个等满 `QUERY_TIMEOUT_MS` 后回退到断连值。

断批 MUST NOT 丢命令：判据 MUST 在取下一条命令之前生效，已出队的命令 MUST 留在通道里
等下一批处理。

实现：`native/src/terminal/ghostty_terminal/internal/mod.rs` 声明
`MAX_COMMANDS_PER_BATCH`（条数界）与 `COMMAND_BATCH_BUDGET`（时长界）；批处理循环在
处理完一条命令后先判上界，再取下一条命令。

#### Scenario: 持续输出下积压被切成有界的若干批

- **WHEN** 命令通道里积压了远超一条批容量的命令，且通道持续有数据
- **THEN** 每一批的条数 MUST 不超过条数上界，批 MUST 在时长上界内结束；
    剩余命令 MUST 留在通道里等下一批，MUST NOT 被丢弃

#### Scenario: 持续输出下查询仍被及时应答

- **WHEN** 终端持续输出，同时发起网格查询
- **THEN** 查询 MUST 在若干批之内被应答，MUST NOT 等到通道排空或超时
