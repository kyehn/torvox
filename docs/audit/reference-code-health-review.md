# 全量代码审查与参考项目对照

本文记录一次覆盖全部被跟踪文件的审查：逐文件读取源码与文档、统一下载并量化参考项目、
对静态扫描的每一处命中逐条判定，最后只保留经得起复核的发现。审查对象为远端主分支的
完整快照；审查期间不修改 `docs/STATUS.md`、不改动任何受保护文件，也不改动源码、测试脚本
或配置。

## 参考项目的相关实践

- termux-app：终端引擎、视图、共享库、应用四模块分离；常量集中于 `TermuxConstants`；
  属性解析用标准库 `Properties`，键白名单作为安全边界；15 组以上 JVM 测试驱动仿真器断言。
- ghostty-android-terminal：Java 视图层与 C 原生层分离，JNI 门面单一职责，另有
  `CLAUDE.md` 记录工程约束。
- termlib：Compose 组件库，输入经每终端一条 FIFO，快照在后台 dispatcher 合并，组合、
  布局与绘制不持有终端锁；Unicode 表由固定版本数据生成入库并提供复现校验；提供
  Roborazzi 视觉基线、帧基准与内存基准。
- awkox/AndroidTerminal：库按引擎、缓冲、协议、颜色、文本、视图分层，视图再分输入、
  交互、生命周期、渲染、选区；其 `AGENTS.md` 首条即要求单一职责，最大源码文件仅 1284 行。
- Drosh：性能规划文档以「关注点 / 手法 / 证据」矩阵对照多个终端，每条现状声称锚定
  固定坐标并标注是否亲读工作树，另设完成定义要求把前后数字写入留档。

## 发现

### 代码规模硬约束缺少可判定口径与门禁

`docs/specification/STYLE.md` 规定「代码量不得超过 ghostty-android-terminal 与 termux
的合计，必须最小实现」，但仓库没有定义「代码量」的口径，也没有把这条约束做成可复算的
门禁。按上表口径：生产代码 38722 低于两者生产之和 49059，源码合计 75622 却高于两者
合计 54380 约三成九。同一条约束因口径不同而结论相反，属于不可判定。

`scripts/check.nu` 与持续集成工作流执行格式、静态分析、单元测试、界面测试与 openspec
校验，但没有任何步骤度量代码规模。`code-health` 规约只覆盖重复夹具、依赖活跃度与扫描
留档，不含规模维度。测试与生产之比为 0.95，是全部对照项目里最高的（termux 0.09、
ghostty-android 0.13、termlib 0.52），说明投入结构与同类项目差异显著，但当前无口径去
判定这是否越界。

根因是规范自我要求「靠固定参数扫描判定、留下可复算的留档」，却唯独对这条最硬的规模
约束没有给出扫描参数与留档位置。解决方案不是删测试——`TESTING.md` 要求高覆盖且每个
测试断言具体结果——而是把口径写死、把度量纳入门禁、把基线数字留档，使约束可判定。

### 超大文件治理标准未跨源码语言一致应用

历史变更 `split-native-oversized-modules` 以固定阈值（约 1100 行）拆分了 11 个原生侧
大文件，设计文档明确「拆分依据是职责，不是行数」。但同一标准从未应用到 Kotlin 侧：
`TerminalRuntime` 5335 行、`TerminalSurface` 4435 行、`TerminalViewModel` 2135 行、
`SettingsScreen` 1303 行仍在，其中前两者规模都超过当年被拆掉的原生文件。全仓 12 个
超过千行的文件里多数在界面与运行时层。

对照 awkox 按职责分层后最大文件仅 1284 行、超过千行文件仅 1 个；termlib 把终端、
仿真器、输入法视图分文件。这是「不如参考项目、也不如自身历史标准」的双重落差。

边界必须说明：`STYLE.md` 反对一次性抽象、要求仅用一次的辅助类型优先内联，因此方案不是
按行数机械拆分，而是沿用历史设计文档的口径，按彼此独立的职责边界重组并留档判定。
`TerminalRuntime` 的方法名聚类显示它同时承载会话生命周期、渲染线程调度、看门狗、
通知、剪贴板、响铃、主题、字体、输入法、选区、滚动与前台服务等十余个关注面，具备
按职责切分的事实基础。

### 设计文档明列的参考项目缺少研究留档

`docs/specification/DESIGN.md` 声明未覆盖的实现细节参考 termux-app、
ghostty-android-terminal 与 termlib 三者。`docs/persistence/` 已有前两者及
`libghostty`、`osc-notifications`、`terminal-protocols` 共五份研究留档，唯独没有
termlib 的对应资料。termlib 恰是同类度最高的参考：同为 Kotlin 与 Compose 界面、经 JNI
接终端引擎，其渲染说明、生成物复现校验、视觉基线与基准体系最值得对照。三个明列参考
中两个有深度留档、一个缺失，属于资料齐备性缺口，可确证且可补。

### 声明的静态检查工具未进入验证门禁

`docs/specification/TESTING.md` 要求使用重复检测与代码质量扫描工具检查代码，
`scripts/check.nu` 实际执行的是格式、静态分析、测试与规范校验，并未调用那两项工具。
历史变更曾用代码质量扫描的「文件过大」与「函数过长」告警作为拆分依据，说明该工具曾可用。
规范声明与门禁实际内容不一致，正是发现一与发现二长期未被自动拦截的原因之一。

## 逐条判定留档

对源码集运行静态形状扫描后，按 `code-health` 规约逐条判定，命中不等于缺陷。

| 扫描类别 | 命中 | 判定 | 可复核依据 |
| --- | --- | --- | --- |
| 变量缩写疑似 cfg | 227 | 误报 | 全部是 Rust 的条件编译属性，不是变量命名 |
| 变量缩写疑似 bg | 16 | 误报 | 全部是完整拼写 `backgroundColor`，无独立缩写 |
| 生产代码 expect | 157 | 不是缺陷 | JNI 硬编码字符串、日志器一次性安装、原子量中毒与字段上界，`DESIGN.md` 要求极端情况尽早崩溃 |
| 生产代码 panic | 20 | 不是缺陷 | `DESIGN.md` 明令极端错误输出日志并崩溃退出；着色器与主题解析失败亦属此类 |
| 硬编码颜色 | 123 | 误报 | 全部是测试里的像素常量与打包掩码；主题颜色按 `DESIGN.md` 构建期产出 |
| 只断言非空 | 8 | 不是缺陷 | 均带具体诊断消息且为前置条件断言，非「只断言不崩溃」 |
| 软件名/被禁 shell 命中 | 4 | 误报 | 命中位置是 `.semgrep/rules.yml` 的规则定义本身 |
| 精确版本 | 2 | 不是缺陷 | 是 `versionName` 与自身包版本，非依赖声明 |
| 生产代码 unwrap | 19 | 不是缺陷 | 均落在测试辅助模块与 PTY 测试，非生产路径 |
| 条件编译之外的 @Suppress | 13 | 不是缺陷 | 均为定点抑制且附理由，`TerminalDispatchers` 集中一处优于多处分散 |
| 跳过/忽略测试 | 0 | 通过 | 与 `TESTING.md` 及 semgrep 规则一致 |
| 未完成实现宏/跳过诊断 | 0 | 通过 | 同上 |
| 禁用环境变量 | 4 | 误报 | 全部是负向测试，断言子进程不设置这些变量 |
| 未受管构建命令 | 12 | 不是缺陷 | 落在构建脚本自身与测试注释，非源码内联命令 |

## 明确不作处置的项

| 候选 | 不作处置的理由 |
| --- | --- |
| 换成桌面终端的 VT 引擎或渲染栈 | `DESIGN.md` 指定 `libghostty-vt` 与 `wgpu`，换核违反架构单一来源 |
| 用绑定生成框架替换手写 JNI | `DESIGN.md` 规定 Kotlin 直接 JNI 调用，且属改源码，超出本次文档范围 |
| 帧循环计数器与帧时间线关联、真实 PTY 捕获重放 | `research-closure` 设计文档已明确评估并否决 |
| 用视觉基线替换现有界面测试 | `TESTING.md` 指定 OCR 与像素断言体系，且属改测试 |
| 删除测试以降低规模 | `TESTING.md` 要求高覆盖，规模问题应由口径与门禁解决 |
| 直接改 `scripts/check.nu` 或工作流加门禁 | 二者是受保护文件，且 `STYLE.md` 禁止提交生成的配置或脚本 |
| 直接拆分大文件 | 属改源码，本次只产出方案与规约，不改实现 |

## 解决方案与优先级

| 优先 | 问题 | 方案 | 落点 | 前置条件 |
| --- | --- | --- | --- | --- |
| 高 | 规模约束不可判定 | 定义统一 SLOC 口径与生产/测试分列，把度量与阈值写进规约，定期复算并留档基线数字 | `code-health` 规约 | 无，纯文档 |
| 高 | 大文件标准双标 | 要求同一阈值跨源码语言一致应用，按职责边界拆分，保留超大文件须逐条留档理由 | `code-health` 规约 | 具体拆分另立变更并需改源码授权 |
| 中 | termlib 研究留档缺失 | 补一份对照资料，覆盖分层、输入顺序、生成物复现校验与基准体系 | `docs/persistence` | 该目录受保护，需明确同意 |
| 中 | 声明工具未入门禁 | 在任务清单登记为待办，明确由受保护文件的维护者决定接入方式 | 变更的 `tasks.md` | 需受保护文件修改授权 |

## 复现方法

统一口径的统计按下列步骤可复算：遍历被跟踪文件，跳过构建产物、第三方代码与生成目录；
按扩展名分组，生产与测试按路径判定；逐行排除空行、纯注释行与块注释；分别汇总生产与
测试行数；对参考项目用同一脚本、同一参数重跑。逐文件覆盖清单、反模式命中明细与
逐条判定结果按轮次留档，可与本文表格逐项核对。
