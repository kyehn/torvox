## 3. 长按与 libghostty 接口

- 必须用且已用：词派生、跟踪选区、随滚动跟随、复制格式化、超链接查询。优势是单一来源，语义与渲染同源；自研即违规。
- 不得用手势状态机五十项：按下拖动释放深按自动滚动计时手势机与行为表。劣势三条：连击语义与禁止多击正面冲突；边缘定时滚动与动则一行静则零行正面冲突；手势状态若由原生持有则每触摸帧一次跨线程往返，快路径零跨越优势尽失，且与组合手势所有权双状态机脱钩。
- 当前分层合理：原生做派生跟踪格式化，界面侧做手势手柄菜单滚动。十二项小问题的逐项现状见 §3.1。

## 9. 复核轮次的验证记录

第十五轮把前三轮因环境受阻的三项门禁补齐，结论全部有命令输出为据。

- **阻断根因有两处，都不在代码里**。其一：宿主沙箱设了 `TMPDIR` 指向会话临时目录，nix 按 `TMPDIR` 建 shell 目录，故 `NIX_BUILD_TOP` 形如 `/tmp/<会话目录>/nix-shell.XXXX`；而 `native/build.rs` 与 `android/build.gradle.kts` 的「必须跑在 nix develop 内」守卫要求前缀 `/tmp/nix-shell.`。显式 `TMPDIR=/tmp` 后守卫自然通过——nix 在其约定的真实布局下建目录，不是绕过检查。其二：`libghostty-vt-sys` 的构建脚本要从 codeberg 取 `translate-c` 归档，该站点一度整体 503；恢复后 zig 全局缓存自动填充（条目名含内容哈希，不可伪造，也无需伪造）。

## 10. 第十七轮：把第十六轮登记的未修项逐条落地

第十六轮留了六条「需更大改动」的项。第十七轮逐条评估：能局部收口的收口，不能的说明为何不改并给出实测证据。

### 10.1 已修

- **看门狗的停止闸门会被重启复位**：`RenderWatchDog` 用布尔 `stopped` 表达「已停止」，而 `start()` 把它复位——同一实例重启时，旧循环（正卡在不可取消的探测里，取消来不及）看到复位后的 `false` 照样回调，把**新**渲染线程误判为死亡。改用单调递增的启动代次，旧循环发现自己过期即无权回调，与调用方是否复用实例无关。新增回归用例**经变异验证**：还原成布尔判据即失败；把轮询条件改成永不满足则 5s 期限判红，证明该例不是恒真。

### 10.2 评估后不改（附理由与证据）

### 10.3 第十八轮续办：原「仍未修」三项的收口

- **取纹理最长阻塞 2s**（已收口）。先核实前提：超时落在 `AcquireOutcome::Skipped` 上，而 `note_surface_acquire` 只对 `SurfaceLost` 推进 `surface_loss_streak`——跳过不判死窗口、下一帧照常重试，连续跳过满 300 帧才记一条 error。故「把期限压到帧级」是安全降级，不需要把 acquire 移出锁（那要重构 `FrameContext` 生命周期，其借用 surface 纹理跨锁持有不安全）。此前渲染路径取 2s、warmup 取 100ms 两条口径不一致；两者都持 `RENDER_STATE` 且被 UI 线程争用，**期限就是这个锁被按住的时长**，故统一为一个 100ms 常量。新增 `repeated_skips_never_invalidate_surface` 钉住「连续跳过永不判死」——若跳过会推进失效计数，这个期限就会把一次慢帧变成永久黑屏。该用例经变异验证：让跳过也推进计数即失败。

## 11. 第十九轮：两条新线的并行深审（Kotlin 安装/文档提供器 + Rust 终端/PTY）

第十八轮把登记项清完后，本轮换了此前**从未深审过**的两块：Kotlin 侧的安装器/文档提供器/设置/前台服务，以及 Rust 侧的 PTY 与终端核心。两份报告共 20 余条，逐条核实后落地如下。

  用例第一版**没有判别力**：默认夜间主题恰是白底黑字，写死色与真实色无法区分，还原后仍全绿；且 `flush()` 一插在写入与查询之间，「该行仍是脏的」这个前提就不成立。改成用 `tokyo_night` 主题、且写入后不 `flush`（让两者落在同一批）才复现。
- **引导安装清不净 staging 区仍继续**（见同名提交）。`delete` 丢弃每个 `File.delete()` 的返回值，`listFiles()` 为 null 时整棵子树被静默跳过；于是「删不掉」与「删干净」无法区分，新引导写进残留旧树，`atomicRename` 把混血树当 prefix 发布，而安装一路报成功。
  用例第一版**也没有判别力**：只读目录放在 `bin/`（ZIP 也要写它），去掉守卫后解压同样失败，两种实现都「失败」；把只读目录挪到 ZIP 不写的 `locked/` 后，去掉守卫即安装成功，断言才真正咬得住。
- **每个 postinst 子进程在成功路径从不销毁**（见同名提交）。`exitCode == 0` 直接 return，`Process` 直到 GC/finalizer 才回收，排空读端也未关闭。一趟真实引导约 250-300 个 postinst，每个泄 2 个管道 fd，Android 进程上限 1024——未及 GC 就用尽会得到 `EMFILE`，表现为后续 `chmod`/开文件抛 IOException 而整次第二阶段失败。
- **`moveDocument` 的自环守卫比 `copyDocument` 严**（见同名提交）。`copyDocument` 的守卫带 `!isSymbolicLink` 限定并注释说明了理由（`copyTreeInto` 遇链接只复制 inode 自身），`moveDocument` 却对 `canonicalFile` 直接判前缀，且注释谎称两处相同。结果「把链接搬进其目标子目录」——一次普通 rename、根本不存在遍历打转——被误拒。两条守卫已对齐，并补了「真目录搬进自身子孙仍被拒」一例防止放松过头。
- **`Pty::write` 不重试 EINTR**（见同名提交）。resize 的 SIGWINCH 与子进程退出的 SIGCHLD 都会打断 `write`，此前原样抛出，FFI 层遂记「子进程未在期限内消费按键，已丢弃」——而这批字节一个都没送出去。
- **`wait_writable` 不看 `revents`**（同上）。主端挂断时 `poll` 立刻返回 > 0 但置的是 `POLLHUP/POLLERR` 而非 `POLLOUT`；无条件 `Ok(())` 会让调用方重入 `write` 拿 EAGAIN → 再次 `wait_writable` → 立刻返回，整段排空期限变成满速空转。

## 12. 第二十轮：消化第十九轮登记项

第十九轮两份报告留下的项逐条走完。**三条用例在过程中暴露出「第一版恒通过」的陷阱**，据实记录如下——这是本轮比修复本身更值得记的部分。

### 12.1 已修

- **PTY 互斥锁把无界写入与销毁串行化**（见同名提交）。`PtyMaster::write` 持互斥量跑完整个 `write_all`，而它每有部分写入就重置期限，故持锁时间**无上界**；`request_exit` 也去取同一把锁，而它经 `destroySession` 跑在 UI 线程上——子进程不读 stdin 时销毁会阻塞主线程，`Session::drop` 的 `join_with_timeout` 随之超时并**分离等待线程**。改为构造期缓存 `child_pid`（进程组在 spawn 后不变，与现取等价），销毁路径彻底不再碰互斥量。
  用例第一版把读取直接放在主线程：变异后**整条用例挂死**（`timeout` 只能杀掉，不会判红）。挂死的用例比判红的更难排查。改为把读取放进另一个线程经 `recv_timeout` 收取，并**先收结果、再放行、最后才断言**，保证任何分支下写入线程都被放出来。
- **待上报剪贴板写入队列无上界**（见同名提交）。其深度说明写着「受 `EVENT_CHANNEL_CAPACITY` 约束」——那只约束上游通道，而 `drain_callback_events` 每帧把通道**排空**进本队列、`poll_clipboard` 每帧只取一条，净增速可达每帧十余条；渲染暂停期消费彻底停摆。改为封顶并丢最旧（与 `clipboard_read` 的洪泛削减同口径），并订正那条不成立的说明。
  用例第一版**在测试里复刻了封顶逻辑**，等于断言自己刚写下的代码，恒通过。改为走真实路径：投进 VT 解析器再反复 `process_output` 收割。首次断言还写错了对象——队列里是**解码后的正文**而非 base64 载荷。
- **VT 线程上的 resize 失败导致 PTY/网格永久分歧**（见同名提交）。`GhosttyTerminal::resize` 只报告命令**是否入队**，而 `Terminal::resize` 真正在 VT 线程执行，其间还隔着一次可能失败的上游调用。此前该失败只记日志：`Session::resize` 已按「已入队」把缓存尺寸发布成新值并清掉 `grid_dirty`，于是同尺寸的下一次走 `!dirty && 尺寸未变` 短路，永久分歧且无重试时机。新增跨线程标记，短路判据一并纳入。
  用例第一版只断言 `grid_dirty`/`resize_failed` 这类**间接量**，还原实现后仍全绿——它根本没观察是否真的重发。改为用 `MockPty::resize_count` 这一确定性可观测量（短路分支根本不碰 PTY）。`internal.rs` 里那个同名的 `grid_dirty` 只是快照重建用的**局部**变量，从不回传到 session 的原子量，这是当初判读时最容易看错的一处。
- **写回通知发到调用方传入的 docId**（见同名提交）。树 URI 客户端传的是 `terminal_home/x.conf`，本提供者行内只发行 `x.conf`，两者是**兄弟** URI 而非祖先/后代，广播到前者收不到——外部编辑器覆写后文件选择器不刷新。改为经 `encodeDocId` 归一，与 `renameDocument` 早已采用的处理一致。
- **引导 URL 去重基线随「清除应用数据」存活**（见同名提交）。去重用 `distinctUntilChanged()`，它的「上一个值」藏在算子内部，`dropPendingBootstrapUrlEdits` 里的 `resetReplayCache()` 碰不到。于是「设为 X → 清除 → 再输入 X」时第二次被抑制，`put` 永不执行：会话内安装仍成功（读 replay 缓存），重启后 URL 又变空。改为受同一互斥量保护的显式基线，随清除一并复位。
- **`row_cache_invalidated_on_resize` 仍有一处偶发**（同一批提交）。上次修掉了「取到 resize 前的旧帧」，但 stats 是**自上次 `take` 以来的累计**，而轮询可能转过若干轮，于是断言混进了 resize 之前那批帧的复用数——转的轮数取决于机器负载，同一实现有时过有时不过（负载下实测失败一次，随后连续三次全绿）。补一次基线清零，使断言与轮询轮数无关。

### 12.2 修了但**没有**用例（据实登记，不冒充已覆盖）

- **写回通知归一**：Robolectric 的 `ShadowParcelFileDescriptor` **不触发** `ParcelFileDescriptor.open` 的 close-notify 回调，故这条路径在 JVM 侧根本无法观测。曾写过一版断言，它之所以「通过」是因为我在同一用例里追加了一次 `renameDocument`，而后者恰好广播了同一个 URI——属于因错误理由通过，已删除该用例。修复本身与 `renameDocument` 的既有处理同形，保留。

### 12.3 仍未修

## 13. 第二十一轮：设备日志与 CI 的两条外部证据

本节的两条都不是深审发现的，而是外部产物直接暴露的：**用户提供的真机 logcat**，与
**CI 连续八次的 connected 结果**。它们各自指向一件深审看不到的事。

### 13.1 真机日志：渲染暂停期的单元帧告警洪水（已修）

**证据**：`运行日志` 中，（时间已移除） 两条 `setRenderPaused:
paused=true`（打开设置页）之后，`ghostty_terminal: cell frame dropped: sending on a
full channel` 以每秒约 40 条的速度持续到日志末尾，近 200 条。

**根因不是「丢帧」而是刻意为之**：暂停期**不消费**单元帧通道——`receive` 是破坏性取数，
暂停帧取走后永不呈现，而 VT 的去重基线也不会重推，那正是「IME 弹出时输入不可见」的
主因（见 `render_inner` 的注释）。帧于是留在通道里，而通道有界；终端继续输出就把它
填满，此后**每一次**推送都失败。

**真正的缺陷是告警本身**：逐条记没有任何诊断价值（每条都只是同一个「通道满」），
却挤爆 logcat 并持续吃 CPU。改为限频 5s（复用本仓已有的 `flood_shed_warn_throttled`
同款写法），恢复后通道排空即自然重新放行。用例经变异验证：去掉限频即判红。

**据此得出的一个反面结论**：深审一直把「暂停期通道被填满」记作可疑项，但读到
`render_inner` 的注释才明白它是有意设计。**告警洪水才是缺陷**，填充不是。

### 13.2 CI：connected 用例集整体性不稳定（未修，属环境）

**证据**：最近八次 `build` 工作流，七次失败、一次成功；失败用例**每次都不同**——
九个不同的测试类轮番出现（DocumentsProviderInstrumentedTest 五次、其余各一两次），
唯一一次成功的那次没有失败用例。

**结论**：这不是某一处回归的表征，而是这套仪器化用例在当前模拟器配置下整体不稳定。
值得注意的是失败面横跨文档提供器、VT 正确性、输入法弹窗、光标/颜色像素验收、行为规格与
引导安装——彼此无共同依赖。

**与本轮改动的关系**：本地 `scripts/check.nu` 全绿（含 `assembleDebugAndroidTest` 编译），
但**connected 用例在本机无法运行**（需模拟器），故本地绿灯不覆盖这一段。就本次失败而言：
`TermuxBootstrapRealTerminalTest` 走的是 `bridge.writeToPty`，而该函数在本轮全部改动中
**未被触及**（`git diff` 可证 `Bridge.kt` 只新增了 `ptyWriteQueue`/`sendToPty` 并改了
鼠标编码）。故不据此判定为本轮引入。

**但有一处必须盯住**：八次失败里有一次是
`HardKeyboardMultipleArrivalTest#multipleEventCharactersArriveExactlyOnce`——它恰好落在
本轮把硬件按键改走批缓冲的路径上。一次不足以定论，可它也可能是别次不稳定里的一次。
**本地无法验证**（需模拟器），故如实登记为「待设备侧复现确认」，不宣称已排除。

同一份日志开头（**2026-10-02**，与 10-13 那次是两个不同会话）记了一次
`（日志数值已移除）
`Java_terminal_emulator_bridge_NativeBridge_prefetchRenderState` → libnative → `abort`。

**已排除**：该导出确在 `jni_export_guard!` 内；`native/Cargo.toml` 未设 `panic` 键
（默认 unwind）；Android 侧经 `cargo ndk ... --profile release` 构建、未追加
`-C panic=abort`。故「panic 未被守卫接住」这一最简解释与配置不符。

**本轮审计顺带把 61 个 `extern "system"` 导出逐个过了一遍**：全部有守卫
（`selectWordAt` 一度看着没有，实际守卫在其委托的 `select_bounds_export` 内部）。
所以「漏网导出」这条路是死的。

**收敛出的真缺陷有两条，都在守卫的 panic 处理路径上**：

1. **解卷中销毁载荷 → 进程 abort。** `on_panic` 拿到的 `Box<dyn Any>` 会在函数返回时
   按值销毁，而那一刻**已经有一个 panic 在途**。若载荷元素的 `Drop` 再 panic，
   就是「解卷中解卷」，Rust 不做二次解卷而是直接 `abort`——这正是守卫接住首个 panic
   之后、在**处理**它时崩掉、调用方连 Java 异常都拿不到的机制。原注释声称已用泄漏
   规避，代码却并未泄漏。已改为 `mem::forget` 整个 `Box`（崩溃路径上宁可漏几字节）。
2. **panic 文本恒被吞掉。** 旧代码写 `panic_text(&payload)`，靠 deref coercion 把
   `&Box<dyn Any + Send>` 转成 `&(dyn Any + Send)`；转出来的 trait object **丢掉具体
   类型**，`downcast_ref` 恒为 `None`。实测对照：同一 `Box` 走 `&*payload` 命中、
   走 `&payload` 落空。后果是**每一个真实 panic 都被报成 "non-string panic payload"**——
   守卫接住了 panic，抛给 Java 的诊断却是一句占位话。已改为 `payload.as_ref()`。

两条都已用变异验证（各自退回旧写法即判红）。第 2 条顺带说明了一件本该早就发现的事：
日志里 panic 诊断之所以一直是空的占位话，不是设备问题，是这个恒失配。

**仍存的界限**：日志是 10-02 的，而上面的修复是本轮才做的，**无法证明当时那一次
abort 就是由第 1 条引起**——那需要该次崩溃对应的构建产物或 commit 才能定论。
已能确定的是：这条路径确实存在、且是唯一能让守卫失效后仍走到 `abort` 的机制，
现已消除；且此后任何真实 panic 都会带上正确的文本，而不是占位话。

### 13.5 更正：CI 不是「随机不稳定」，而是一次一个确定根因

本节初稿把 CI 的失败说成「用例集整体性不稳定、每次失败用例都不同」。**那是错的**——
把「每次不同」直接推断成「随机」是本末倒置。逐次归因后，真实图景是**每一次失败都有
一个确定根因，只是根因不同**；修好一个就露出下一个。

| 运行 | 根因 | 波及用例 |
| --- | --- | --- |
| 10-11 两次 | 文档提供者冲突命名插错位置（`(2)` 插在扩展名前） | 1 |
| 10-12 09:09 | 同上 + VT 光标断言的 shell 竞态 | 3 |
| 10-12 10:00 | ——（冲突命名断言修复后） | **0，通过** |
| 10-12 14:24 | **surface 配置失败 → 渲染全灭** | 6 |
| 10-13 05:52 | 引导安装用例的输出未在固定等待内落地 | 1 |

两个关键事实：

1. **「每次用例都不同」不等于随机。** 10-11/10-12 那几次的失败全部落在
   `DocumentsProviderInstrumentedTest#tree_uri_modify_copy_move_round_trip`，且断言消息
   **逐字相同**——那是确定性失败，不是 flake。它随那次「订正文档冲突命名断言」的提交修复，该次运行随即通过。
   我一度把它当成「尚未修复的确定性缺陷」继续追查，看到该提交的日期才发现自己拿的是
   **过期失败**。教训：判定「是否已修」必须核对修复提交的时间与 CI 运行时间。
2. **10-12 14:24 那次的 6 个失败共用一个根因。** 失败消息高度一致：光标反差 = 0、
   SGR 三色 = 0/0/0、斜体差分 = 0、输入法条带无内容像素、中文未落格——**全是「什么都没
   渲染/输入没进去」**。同一次运行里另有 2 条 `Surface::configure` /
   `GPU_UNCAPTURED` / `UnsupportedQueueFamily`。即：surface 配置失败 → 渲染线程起不来
   → 所有依赖渲染的断言一起归零。一个根因，六种表现。

**本轮据此修掉一处真缺陷**（见 §13.3 丁类，`attach_surface` 的失效位清零时机）。

**如实登记「没有 seam」**：该修复**配不出判别力足够的用例**。`attach_surface` 带
`#[cfg(target_os = "android")]`，宿主上根本不存在；`Renderer` 的构造又需要真实 GPU。

  KDoc 与设置页的「px」标签都按物理像素读。高密度设备上设置页显示的单元格会比实际
  渲染小一个密度倍数（同屏的字号行却正确做了 sp→px）。改为上报前乘 `raster_scale`，
  并订正 `FontInfo.font_size` 注释里把 density 重复乘一次的说法。
- **样式面字形号缓存容量取错了参照**。它与 (字体, 粗, 斜) 三元组缓存共用 64 条，而它的
  键是 (面, 码位)：一屏 40×20 就是 800 个不同码位，必然穿透，每次未命中都要重入
  `with_face_data` 重建 charmap（字体解压）。改为独立定容 4096，用例
  `styled_screenful_of_codepoints_stays_cached` 用 200 个不同汉字的粗体渲染钉住。
- **CJK 回退族名被归一成不存在的名字**。`Noto Sans CJK SC`/`TC`/`JP` 等真实族名被合并
  成字面量 `"Noto Sans CJK"`：既违反「不硬编码字体名」，也让用户按名找不到该字体，还与
  本函数 KDoc 承诺的「首元素即实际渲染命中者」相悖。改为只去重、报真实族名。
- **后台会话的 OSC 52 读请求队列无界增长**。`take_clipboard_reads()` 只在活跃分支调用，
  而后台分支的 `poll_pty_output` 照常把请求压进队列——进一条、从不取出，且那些程序永远
  收不到应答。原注释还宣称「深度天然有界」，是条假声明。后台分支改为同样收割，走同一条
  削减路径。用例构造后台会话灌入超过单会话上限的读请求，断言 PTY 上出现空串应答。
- **洪泛削减的回写本身没有上界**。削减分支要同步写 PTY（子进程不读 stdin 时每次可等到
  50ms），而它在渲染线程上：一个 8KB 输出块约 900 条读请求，一帧十块即约 9000 次带锁
  写入。实测去掉上界时单帧 3632 次削减回写。改为每帧至多 16 次（超出即不写，不写即拒绝）。
  两条用例共用一把注册表锁串行化——注册表与活跃会话 id 是进程级全局量，并行跑会互相
  偷走对方的读请求。
- **超长选择器名告警无节流**：病态远端每几十字节触发一次，逐条记淹没 logcat。同仓同类
  路径（渲染洪泛、事件队列溢出）都已限频，此处是遗漏。
- **panic 消息含内嵌 NUL 时整条日志被写成空行**：改为截断到第一个 NUL 之后。崩溃现场里
  常带用户可控字符串，丢掉整条等于丢掉现场。**无单测**：该模块 `#![cfg(target_os =
  "android")]`，宿主编译不到，据实登记不冒充已覆盖。
- **着色器从不读取的光栅缩放 uniform**：`Uniforms.raster_scale` 只被写入、从不读取
  （字形按 1:1 采样，再乘一次反而缩回逻辑像素）。连带 `Renderer::set_raster_scale`
  只是每帧多传一个从不参与运算的数。两侧同时删除，std140 尾部对齐改为显式 `vec2`
  补足 80 字节（否则 wgpu 以「绑定小于 min_binding_size」拒绝整个管线）。
- **字体侧单字母变量**（atlas 分配、整形缓冲复用、CJK 段起点、度量回退）按 STYLE 改名。

### 16.2 复核为误报（附排除依据，不改）

- **8 位 ST（`0x9C`）与 8 位 OSC（`0x9D`）不被拦截 OSC 52 读请求**：实测上游在 UTF-8
  流里把 `0x9B`/`0x9D`/`0x9C` 当非法字节替换成 U+FFD 并当文本落格（见本文件 §6.3 的
  语料 16）。也就是说**上游自己也不把 8 位控制当控制符**；本仓若单独拦截，反而制造出
  上游没有的语义。语料回放已把该行为钉住。
- **`ShellEnv::default()` 产出 `HOME=/` 且无 PREFIX**：`prefix` 为空串是**生产在用**的
  取值——failsafe 会话与「引导程序未装」时 Kotlin 明确传空（`TerminalRuntime.buildConfig`），
  此时本就该无 PREFIX。空 home 才是可疑输入，但 Kotlin 生产路径从不传空，改为抛错只会把
  防御分支变成新的失败面；记录不改。
- **`getFontInfo` 打包 61 字节与注释里的「60 字节颜色」**：1（暗色标记）+ 4×3 + 16×3 = 61，
  注释说的是「暗色标记与 60 字节颜色」，自洽。
- **`cache_stats` 计入行级复用是否真的只走抽取路径**、**`clear_identity_caches` 是否漏清
  `style_glyph_id_cache`/`outline_cache`**：两者的键分别是 (面, 码位) 与 (面, 字形, 栅格
  尺寸)，都不依赖字号/locale；fontdb 的 ID 在追加面时不重排，charmap 结论稳定。

### 16.3 后续清理（本轮继续做完）

- **字形前进宽度整条链路**：`GlyphInfo.advance_width` → 单元实例的顶点属性 → 顶点输出 →
  片元输入，而片元着色器从未读取它（采样早已改为 1:1，注释里还留着「按 advance 缩放会
  拉伸 CJK」的历史说明）。删它的收益不止于死代码：可变字体路径原本为算这个**从不参与
  运算的数**而逐字调用 `scale_outline`（轮廓缩放）。实例从 96 字节降到 92，顶点属性少一项，
  两条按 advance 断言的旧用例改写为「CJK 位图非空且不超过两格」——那才是当前渲染真正
  依赖的条件；另两条「advance ≈ 格宽」的用例由 §16 之外新增的字体表基准（直接读字体
  的 hmtx）取代，覆盖更强。

### 16.4 新登记但本轮不改（附理由）
